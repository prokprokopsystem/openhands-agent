# Черновая архитектура и план

Документ является первой версией. Архитектура будет уточняться после полной сверки паспорта инфраструктуры и актуальной документации OpenHands.

## 1. Предлагаемая архитектура

```text
Пользовательские устройства
  ├─ домашний компьютер
  ├─ рабочий компьютер
  └─ телефон
          │
          ▼
Защищённый HTTPS-доступ
          │
          ▼
Единый веб-интерфейс
  ├─ чат
  ├─ голос
  ├─ файлы и фотографии
  ├─ история задач
  └─ подтверждение действий
          │
          ▼
Оркестратор агента
  ├─ OpenHands как инженерное ядро
  ├─ выбор внешней LLM
  ├─ управление сессиями
  ├─ таймауты и остановка задач
  └─ журнал действий
          │
          ▼
Изолированные рабочие среды
  ├─ отдельный sandbox на задачу или проект
  ├─ Git-репозитории
  ├─ терминал внутри sandbox
  ├─ браузер
  └─ временные файлы
          │
          ▼
Шлюз инструментов и разрешений
  ├─ GitHub
  ├─ n8n
  ├─ Nextcloud
  ├─ Notion
  ├─ SSH
  ├─ Docker
  └─ будущие MCP/API-инструменты
```

## 2. Почему не следует давать OpenHands прямой полный доступ ко всему

OpenHands должен выполнять инженерные задачи, но доступ к инфраструктуре необходимо выдавать через контролируемые инструменты. Это позволит:

- не передавать агенту основной Docker socket без необходимости;
- ограничить доступ конкретными репозиториями и каталогами;
- разделить чтение и изменение;
- записывать каждую операцию;
- требовать подтверждение перед опасными действиями;
- заменить OpenHands в будущем, сохранив интерфейс и инструменты.

## 3. Предварительное разделение компонентов

### Компонент A — интерфейс

Должен давать удобство уровня обычного AI-чата. Необходимо отдельно проверить, достаточно ли штатного GUI OpenHands для телефона, голосового ввода, фотографий и управления несколькими проектами. Если недостаточно, перед OpenHands устанавливается отдельный веб-интерфейс.

### Компонент B — OpenHands

Используется как инженерное ядро для:

- анализа репозиториев;
- написания и изменения кода;
- терминальных операций внутри sandbox;
- запуска тестов;
- работы с браузером;
- подготовки diff, commit и pull request;
- создания автоматизации и других агентов.

### Компонент C — шлюз инструментов

Единое место подключения внешних систем. Предпочтительные способы:

1. официальная интеграция;
2. MCP-сервер;
3. ограниченный API-wrapper;
4. n8n webhook или workflow;
5. SSH-wrapper с белым списком команд.

### Компонент D — модель

LLM выполняется внешним провайдером. Конфигурация должна позволять менять модель, не меняя интерфейс, рабочие среды и интеграции.

## 4. Этапы проекта

### Этап 0 — инвентаризация

- прочитать паспорт инфраструктуры;
- выписать mini-server, VPS, сети, домены, reverse proxy, Docker и занятые порты;
- определить доступные ресурсы mini-server;
- отметить сервисы, которые запрещено изменять;
- составить карту возможных подключений.

Результат: `docs/03-infrastructure-fit.md`.

### Этап 1 — проверка OpenHands без подключения к инфраструктуре

- выбрать актуальную стабильную версию;
- запустить отдельный тестовый экземпляр;
- подключить одну внешнюю модель;
- проверить GUI с компьютера и телефона;
- проверить текст, файлы, изображения, историю и остановку задачи;
- измерить потребление памяти, процессора и диска;
- проверить восстановление после перезапуска.

Результат: решение, подходит ли штатный GUI или нужен отдельный интерфейс.

### Этап 2 — безопасная базовая установка

- отдельный каталог проекта;
- отдельный Docker Compose;
- отдельная сеть;
- постоянные volumes;
- HTTPS и авторизация;
- healthcheck;
- restart policy;
- резервное копирование конфигурации;
- отсутствие прямого доступа к production-сервисам.

### Этап 3 — GitHub

- доступ только к выбранным репозиториям;
- работа через отдельные ветки;
- запрет прямого изменения `main`;
- просмотр diff перед commit;
- подтверждение перед push и pull request;
- журнал действий.

### Этап 4 — n8n

- сначала read-only изучение workflow;
- экспорт workflow перед изменением;
- создание черновых workflow отдельно от production;
- тестирование через тестовые webhook;
- подтверждение перед активацией или заменой production workflow.

### Этап 5 — Nextcloud и Notion

- ограниченный доступ к отдельным каталогам и базам;
- сначала чтение и поиск;
- затем создание новых объектов;
- изменение и удаление только после подтверждения;
- AMNESIA не затрагивается.

### Этап 6 — SSH и Docker

- не выдавать unrestricted shell сразу;
- использовать отдельного системного пользователя;
- применить wrapper и белый список операций;
- разделить диагностику, deployment и опасные административные действия;
- полный Docker socket рассматривать только как крайний вариант.

### Этап 7 — голос, Telegram и дополнительные интерфейсы

- голосовой ввод в веб-интерфейсе;
- при необходимости Telegram как дополнительный, а не основной интерфейс;
- уведомления о завершении длительных задач;
- продолжение одной сессии с разных устройств.

### Этап 8 — эксплуатация

- резервное копирование;
- обновление через тестовый контур;
- мониторинг состояния;
- периодическая проверка восстановления;
- документирование новых инструментов и разрешений.

## 5. Критерии приёмки первой рабочей версии

Первая версия считается принятой, если одновременно выполнено следующее:

1. интерфейс доступен с домашнего ПК, рабочего ПК и телефона;
2. доступ защищён авторизацией и HTTPS;
3. пользователь работает через графическое окно, а не через консоль;
4. поддерживаются текст, вставка, файлы и фотографии;
5. голосовой ввод работает либо штатно, либо через согласованный дополнительный компонент;
6. агент выполняет задачу в отдельной sandbox-среде;
7. агент может прочитать выбранный GitHub-репозиторий, создать ветку и подготовить diff;
8. push или изменение production не выполняется без подтверждения;
9. зависшую задачу можно остановить из интерфейса;
10. после перезагрузки mini-server система запускается автоматически;
11. сбой агента не нарушает работу существующих сервисов;
12. конфигурацию можно восстановить из резервной копии;
13. действия и ошибки видны в понятном журнале.

## 6. Условия отката

Откат выполняется, если:

- агент мешает работе действующих сервисов;
- mini-server испытывает нехватку ресурсов;
- интерфейс регулярно зависает;
- задачи невозможно остановить;
- обнаружен неконтролируемый доступ к Docker, SSH, файлам или секретам;
- обновление нарушает рабочую версию;
- новый инструмент выполняет действия вне выданных разрешений.

Минимальный механизм отката:

1. остановить только контейнеры проекта `openhands-agent`;
2. вернуть предыдущий зафиксированный Compose и конфигурацию;
3. восстановить volumes из последней проверенной копии при необходимости;
4. не изменять контейнеры, сети и данные других проектов;
5. записать причину отката и результаты проверки.

## 7. Открытые вопросы

- достаточно ли штатного OpenHands GUI для телефона, фотографий и голоса;
- нужен ли Open WebUI или собственный frontend;
- какие модели будут основными и резервными;
- где должен находиться шлюз инструментов;
- как безопасно подключаться к удалённому n8n;
- какие аппаратные ресурсы mini-server реально свободны;
- какие домен, порт и схема авторизации будут использоваться;
- какие операции каждому инструменту разрешены без подтверждения.
