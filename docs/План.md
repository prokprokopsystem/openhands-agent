- **TEST MODE** — текущая жёсткая изоляция, пустой `test-workspace`, без доступа к внутренним интеграциям.

## Этап 4D — Постоянные управляемые инструменты агента 🔄

**Цель:** предоставить агенту Canvas постоянные, расширяемые и безопасные инструменты для самостоятельной работы над проектом без ручной настройки каждого действия.

**Принцип:** не искусственное урезание, а контролируемая расширяемость. Агент получает инструменты по уровням риска. Добавление новых инструментов — через реестр, без переделки архитектуры.

### 4D.1 — Инвентаризация существующих возможностей

- Определить, какие возможности уже доступны Canvas (GitHub-доступ, Telegram-шлюз, чат)
- Описать фактическое разделение между контейнером Canvas, мини-сервером, VPS и внешними сервисами
- Перечислить существующие механизмы backup, журналирования и отката
- Найти существующие wrapper, скрипты и решения, чтобы не создавать дублей
- Проверить связанные документы и DEC

### 4D.2 — Архитектура постоянных инструментов

Спроектировать единый расширяемый механизм, состоящий из:

| Компонент | Назначение |
|-----------|-----------|
| Агент Canvas | Принимает задачу, раскладывает на инструменты, выполняет |
| Защищённый канал связи | SSH + ключи для каждого сервера |
| Broker/wrapper | Посредник на управляемом хосте, исполняет команды от имени агента |
| Реестр инструментов | Декларативное описание доступных операций |
| Политика разрешений | Уровни A / B / C |
| Журнал действий | Аудит всех операций |
| Механизм проверки | Валидация результата после каждой операции |
| Резервное копирование и откат | Перед изменениями — backup, при неудаче — откат |
| Адаптеры серверов/сервисов | Отдельные учётные данные и политики на мини-сервер, VPS, GitHub, n8n |

**Ключевые решения:**
- Для мини-сервера и VPS — отдельные учётные данные, отдельные политики, отдельные журналы
- Не один общий ключ для всех машин
- Broker не даёт полный root-доступ, NOPASSWD:ALL, docker.sock или бесконтрольный доступ к секретам

### 4D.3 — Уровни операций

**Уровень A — выполняется автоматически:**
- Диагностика, просмотр состояния, чтение безопасных журналов
- Проверка диска, памяти, сети и служб
- Проверка конфигурации
- Просмотр файлов проекта и документации
- Тесты и проверки работоспособности

**Уровень B — выполняется автоматически в пределах управляемого проекта:**
- Создание резервной копии
- Изменение файлов проекта, редактирование документации
- Сборка и обновление контейнеров проекта
- Запуск, остановка и перезапуск служб проекта
- Применение проверенной конфигурации
- Выполнение тестов, безопасный откат проекта
- Операции с разрешёнными n8n workflow
- Commit и push в разрешённые GitHub-репозитории

**Уровень C — только после явной команды пользователя:**
- Изменение firewall и внешнего доступа
- Изменение SSH, создание/удаление системных пользователей
- Изменение хранилищ и дисков
- Операции за пределами управляемых проектов
- Удаление значительных объёмов данных
- Изменение системы резервного копирования
- Работа с новыми секретами
- Необратимые операции, действия, способные остановить другие сервисы

Если пользователь прямо дал команду на такое действие — это считается подтверждением. Повторные подтверждения того же действия не требуются.

**Всегда запрещены:**
- Вывод секретов в чат или журналы
- Отключение аудита для сокрытия действий
- Выполнение команд вне поставленной задачи
- Доступ к чужим проектам без отдельного разрешения
- Бесконтрольное рекурсивное удаление данных

### 4D.4 — Расширяемый реестр инструментов

Реестр структурированных операций. Для каждого инструмента:

| Поле | Назначение |
|------|-----------|
| Имя | Уникальный идентификатор |
| Назначение | Что делает |
| Целевой сервер/сервис | Где выполняется |
| Допустимые параметры | Ограниченный набор |
| Уровень риска | A / B / C |
| Предварительная проверка | Что проверить до выполнения |
| Команда выполнения | Шаблон команды |
| Проверка результата | Как убедиться, что сработало |
| Способ отката | Как вернуть как было |
| Скрытие секретов | Какие поля маскировать |
| Журналирование | Куда и что писать |

Добавление нового инструмента — отдельным адаптером, без изменения механизма broker. Если инструмента нет — агент готовит адаптер, проверяет и добавляет по правилам.

### 4D.5 — Работа с секретами

- Секреты хранятся на целевом сервере или в предназначенном хранилище
- Агент обращается к секрету по имени или ссылке
- Секрет не передаётся в модель, чат, GitHub, diff или журнал
- Разные сервисы — отдельные ключи
- Существующие ключи других агентов не изменять и не отзывать
- Замена/отзыв одного ключа не останавливает остальных агентов

### 4D.6 — Надёжность

Перед применением изменений агент должен (когда применимо):
1. Определить текущее состояние
2. Проверить свободные ресурсы
3. Проверить конфигурацию
4. Создать резервную копию
5. Подготовить план отката
6. Применить изменение
7. Проверить службу и пользовательский результат
8. При неудаче — автоматический безопасный откат
9. Записать результат в журнал
10. Актуализировать документацию только по подтверждённым фактам

Операции должны быть по возможности идемпотентными.

### 4D.7 — Этапы внедрения

**Этап 2:** техническая спецификация 4D, модель угроз, определение формата реестра инструментов

**Этап 4:** первоначальные инструменты мини-сервера (диагностика, журналы, управление службами проекта, Docker Compose проекта, backup, обновление, откат, документация)

**Этап 5:** адаптер для VPS (отдельные ключи и разрешения)

**Этап 6:** инструменты для n8n (просмотр, экспорт, проверка, изменение, активация/деактивация, откат)

**Этап 8:** сквозное испытание — пользователь ставит задачу, агент самостоятельно диагностирует, изменяет, проверяет, исправляет ошибки, обновляет документацию, выдаёт отчёт
