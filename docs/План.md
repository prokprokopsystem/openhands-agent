# OpenHands Agent — План

**Версия:** 1.1 (26 июля 2026)
**Единая нумерация этапов.** Все документы ссылаются на эту нумерацию.

---

## Режимы проекта

- **TEST MODE** — текущая жёсткая изоляция, пустой `test-workspace`, без доступа к внутренним интеграциям.
- **WORK MODE** — тот же Agent Canvas, systemd, supervisor и контейнер, дополненные отдельным постоянным профилем разрешений и инструментов.

Переход в WORK MODE не требует переписывания базового deployment. Рабочие полномочия подключаются отдельной конфигурацией после успешного тестового запуска.

## Этап 0 — Инвентаризация ✅

- Read-only проверка mini-server (CPU, RAM, диск, Docker, сеть, порты)
- Карта ресурсов
- Вывод: готов к установке

## Этап 1 — Исследование платформы ✅

- Выбор: Agent Canvas v1.6.1 (старый Local GUI deprecated)
- Проверка образа через GHCR manifest (архитектура, пользователь, порты, volumes)
- Вывод: подходит, Docker-режим, без docker.sock

## Этап 2 — Дизайн развёртывания ✅

- compose.yaml с фиксированным digest, healthcheck, изоляцией
- Скрипты: prepare, start, stop, status, logs, purge-test
- Systemd unit
- Egress-политика (правила, проверка)
- Вывод: готов к тестовому запуску

## Этап 3 — TEST MODE: первый тестовый запуск ✅

**Только с пустым test-workspace. Без GitHub, SSH, n8n, Nextcloud, Notion.**

- Выполнить prepare.sh на mini-server
- Запустить контейнер
- Проверить WebUI (текст, файлы, фото)
- Проверить авторизацию
- Проверить остановку/перезапуск
- Проверить egress-изоляцию
- Замерить CPU/RAM
- Остановить, зафиксировать результат

## Этап 4 — WORK MODE: постоянный профиль разрешений и инструментов ✅ (4A)

**Выполняется только после успешного завершения этапа 3 как отдельный ограниченный этап.**

- Сохранить базовый Agent Canvas, systemd, supervisor, контейнер и deployment без переписывания.
- Подключить рабочие разрешения отдельной конфигурацией/профилем.
- Предоставить постоянный доступ к n8n, разрешённым базам Notion, выделенным папкам Nextcloud, AMNESIA и разрешённым операциям GitHub.
- Обычные действия внутри профиля выполнять без ручного подтверждения каждого шага.
- Применить технический шлюз разрешений, который ограничивает доступные ресурсы и операции независимо от агентного ядра.
- Требовать подтверждение только для массового удаления, production deployment, операций с `main`, ключами, firewall, `sudo` и system services.
- Проверить границы профиля и невозможность выхода за выданные полномочия.

## Этап 4C — Integration Security: аудит secrets и проектирование ✅

**Аналитический этап — изменений инфраструктуры не требуется.**

- Аудит механизмов secrets Agent Canvas 1.6.1
- Модель хранения credentials: `/srv/openhands-agent/secrets/`, не в Git, не в `/projects`, не в `profiles/*.json`
- Архитектура Telegram-гейта: отдельный сервис, токен не в контейнере агента
- Разделение Этапа 5 на 5A–5E

## Этап 5 — Эксплуатация

### 5A — Поддержка со стороны хозяина

- Read-only мониторинг Canvas и healthcheck
- Уведомление при сбое (после 5C)

### 5B — Healthcheck и мониторинг

- Существующий docker healthcheck (уже работает)
- `systemctl status` мониторинг
- Новый сервис не добавляется

### 5C — Текстовый Telegram-бот через long polling

- Новый бот (не AMNESIA)
- Только chat_id Игоря, без групп
- Gateway снаружи контейнера агента
- Long polling → Agent Canvas API → ответ

### 5D — Голосовые сообщения через Telegram

- Приём голосового → распознавание речи → Agent Canvas
- Способ распознавания — отдельное решение

### 5E — Ручное обновление и откат

- `docker pull` нового digest → compose → `systemctl restart`
- Откат: старый digest
- Версия образа фиксирована

### Публичный домен и HTTPS — отдельный необязательный этап

- Canvas остаётся WG-only
- Вынесен за пределы Этапа 5
