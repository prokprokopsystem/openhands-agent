## Цель
Локальная долговременная память с поиском по смыслу и по точным словам, по нескольким проектам, с проверяемыми ссылками на первоисточники, версиями/датами и актуальностью. Сохранять полную историю локально, выдавать DeepSeek только относящиеся к запросу фрагменты; избегать лишних вызовов дорогих моделей.

Проверить, поддерживается ли DeepSeek через совместимый интерфейс; эмбеддинги предпочтительно локальные при допустимой нагрузке. Рассмотреть встроенные простые альтернативы до установки дополнительных сервисов.
3. **GitHub**: по-прежнему только проверенные решения, код, инструкции, версии, ссылки на источники; не отправлять сырые разговоры, секреты и персональные сведения.
4. **Архив**: использовать существующую общую систему архивирования на внешнем диске, добавить логический раздел agent-memory. Физический путь, формат и механизм неизвестны до проверки. Не создавать второй независимый backup-сервис.

## Жизненный цикл данных
- Запись: первичное событие и исходный документ остаются неизменными; выделенные из них факты имеют source_id, проект/темы, timestamp, версию, статус актуальности и ссылку на источник. Новый факт не перезаписывает без следа старый.
- Поиск: сначала локальный индекс (гибрид точного + семантического поиска), затем при необходимости оригинал, другие проекты, GitHub или подключённый архив. Фрагменты с источниками и бюджетом токенов.
- Рост: измерять фактические объёмы диска, число событий, размер индекса и время поиска. Никакой автоматической удаления «по возрасту», пока не подтверждены восстановимость, контрольные суммы и поисковая доступность архива.
- Архивирование: согласованная инкрементальная копия на внешний диск, манифест, хеши, проверка восстановления. Отдельная запись статуса архива и указатель в локальном каталоге. Недоступность внешнего диска не должна блокировать основную работу; извлечение из холодного архива сообщает об отсутствии диска, а не выдумывает содержимое.
- Уплотнение: агрегировать старые производные индексные записи и устранять дубликаты только с сохранением ссылок на первоисточник. Сжатие исходных архивов возможно лишь без потерь; LLM-сводки не считаются заменой оригинала.
- Очистка: только после успешного восстановления тестовой архивной записи и подтверждения границ удаления. На этапе пилота **ничего автоматически не удалять**.
- Безопасность: секреты, приватные ключи, токены и личные документы не отправлять в GitHub или внешнюю LLM для индексирования без отдельного разрешения; исключить их на этапе прототипа.

## M3, этап 1 — автоматическое чтение памяти (реализовано и проверено 31.10.2026)

Сделан только первый этап M3: **чтение**. Запись (`Stop`), очередь и восстановление после сбоя не подключались — это следующий отдельный этап.

### Что установлено

Один ambient-плагин OpenHands. Ни новых сервисов, ни контейнеров, без изменений runtime, Canvas, compose, systemd и профилей:

| Файл | Назначение |
|---|---|
| `~/.openhands/plugins/memory-pilot/.plugin/plugin.json` | манифест плагина |
| `~/.openhands/plugins/memory-pilot/hooks/hooks.json` | один хук `user_prompt_submit` (command, timeout 25 s, без `async`) |
| `/projects/memory-pilot/scripts/hook_recall.py` | поиск в существующем Mem0 → JSON `{"additionalContext": …}` в stdout |
| `memory-pilot/plugin/…`, `memory-pilot/scripts/hook_recall.py` | копии в репозитории (установка и откат) |

Хуки читаются при создании беседы, поэтому плагин подхватывается **без рестарта** службы и действует во всех новых чатах. Подтверждение: в новой беседе `hook_config.user_prompt_submit` содержит `mem0-recall`, а `stop`, `session_start`, `session_end`, `pre_tool_use`, `post_tool_use` — пустые (запись не подключена).

### Как работает

1. Пользователь отправляет сообщение → OpenHands запускает хук (stdin: JSON события с полем `message`).
2. `hook_recall.py` ищет в коллекции `m2_memories` (`agent_id=m2-pilot`, `top_k=8`), отбрасывает устаревшее (`superseded_by`), дедуплицирует, берёт не более 4 фрагментов.
3. Печатает ровно один JSON-объект с `additionalContext`: до 1400 символов; каждый фрагмент помечен `project_id · source_path · §section · дата`.
4. SDK добавляет этот текст в `MessageEvent.extended_content` пользовательского сообщения.

LLM в хуке не вызывается: embedder — локальный fastembed, хранилище — встроенный Qdrant, внешних запросов и телеметрии нет (`MEM0_TELEMETRY=False`).

### Отказоустойчивость

- Любая ошибка → `exit 0` **без вывода**: чат продолжается как обычно.
- Qdrant в local-режиме молча создаёт пустую базу по отсутствующему пути — это выглядело бы как «воспоминаний нет». Поэтому до открытия проверяются путь хранилища, наличие коллекции и непустой счётчик; при провале один раз за сессию выдаётся честная строка degraded-mode, дальше хук молчит.
- Посторонний вывод библиотек (предупреждения mem0/fastembed/spaCy) уводится в stderr, а реальный stdout держится отдельным дескриптором, поэтому библиотечный шум не может сломать разбор JSON.

- **Сбой индекса**: при перенесённом хранилище — `exit 0`, одна строка degraded-mode, посторонняя пустая база не создана, хранилище восстановлено и поиск снова работает.

### Цена и ограничения

- **+3.0–3.3 с к каждому сообщению.** Хук синхронный (`subprocess.run` внутри event loop), поэтому это пауза и для остальных бесед. `async: true` не подходит: асинхронный хук не может вернуть `additionalContext`.
- Один поисковый запрос на сообщение; смена темы внутри одного сообщения не разбивается на несколько запросов.
- Порог релевантности не калиброван: при слабом совпадении в контекст попадут нерелевантные фрагменты (ограничено 4 шт. / 1400 символов).
- Латентность зависит от кеша модели fastembed в `store/models`; ephemeral `/tmp` не используется.

### Как отключить (простое)

Мгновенно, без рестарта и без правки настроек:

```
mv ~/.openhands/plugins/memory-pilot ~/.openhands/plugins/memory-pilot.off
```

Новые чаты сразу работают без памяти; уже открытые беседы продолжают использовать ранее загруженный конфиг.
Мягкий вариант без переноса каталога: `mv ~/.openhands/plugins/memory-pilot/.plugin/plugin.json{,.off}` — плагин перестанет загружаться, в лог уйдёт предупреждение.
Откат кода — `git revert` соответствующего коммита; установка с нуля — копирование `memory-pilot/plugin/*` в `~/.openhands/plugins/memory-pilot/`.

### Уточнение к отчёту M3a

Поле `hook_config` в `StartConversationRequest` **существует** и принимается по API (`POST /api/conversations`), но Canvas его не заполняет и в UI такой настройки нет. Поэтому выбран ambient-плагин: он действует на все новые чаты без участия клиента.

### Что не сделано (осознанно)

Автоматическая **запись** результатов, обработка `Stop`/`SessionEnd`, очередь с checkpoint/offset и восстановление после сбоя не реализованы. Критерий «память без ручных команд во всех новых чатах» закрыт пока только по чтению; запись остаётся обязательным следующим шагом.

### Испытание M3 №2Б — минимальная актуализация (31.10.2026)

Полный протокол: **`docs/Память-M3-тест2Б-2026-10-31.md`**. **Механизм PASS, полнота сигнала FAIL — PASS не объявляю.** Штатная операция `update(memory_id, metadata={"status": "superseded", "superseded_by": <K3>})` действительно снимает отменённое решение: metadata сливается с payload (текст и `created_at` целы), `get()` отдаёт указатель, `history` пишет `UPDATE`. Обычный поиск исключает отменённую запись **только** через `expiration_date`, и дата должна быть обратной — сегодняшняя не исключает (сравнение строго `< сегодня`); metadata-флаг сам по себе не исключает ничего, а фильтр `{"status": {"ne": "superseded"}}` на неразмеченных записях даёт 0 попаданий, то есть требует сплошной разметки всех записей. Исторический поиск сохраняет отменённое (`show_expired=True` — 5 записей, фильтр `status=superseded` — 1). Состояние переживает перезапуск процесса. Сопоставление индексов `linked_memory_ids` с реальными UUID **восстановлено и доказано** (секция `## Existing Memories` из промпта + уникальность текста + порядок выдачи векторного поиска: 2/2, порядок совпал), но Mem0 сам его не отдаёт — `uuid_mapping` создаётся в `main.py:937,939` и нигде не читается. Препятствие: сигнал модели покрыл **1 из 2** записей про K2, поэтому активная запись «K2 проверено испытанием и работоспособно» осталась и выдаётся обычным поиском (0.214) — противоречие не устранено, полноту сигнала изнутри Mem0 проверить нечем. Стоимость: 2 вызова, 18 439 токенов, 8.09 с; актуализация LLM не вызывает.

### Испытание M3 №3 — актуальное решение по каноническому документу (31.10.2026)

Полный протокол: **`docs/Память-M3-тест3-2026-10-31.md`**. **PASS.** Схема «Mem0 ищет — документ решает» работает на существующих средствах, без новых сервисов. Канонический `Решения.md` (дата пересмотра 31.10.2026) даёт действующее решение (Q0.2 → **K3**), отменённое (**K2**), причину и ссылку на источник; Mem0 отдаёт релевантные записи, включая противоречивые: снятую `47230f3d` (`status=superseded`, `superseded_by=8050a6f4`, `expiration_date=2026-10-30`) и оставшуюся активной `f632a54d` («схема с K2 проверено и работоспособно» — остаток неполного сигнала из №2Б). Ни одна запись не удалена; действующим K2 не выдаётся. Контрольный опыт: документ-вариант с **K4** победил top-1 Mem0 (K3, 0.297) — то есть актуальность определяет документ, а не близость. Негативный сценарий (`missing`, `unreadable`) — действующее решение **не подтверждается** ни по K2, ни по K3, хотя Mem0 продолжает возвращать K3 первым. Три независимых процесса дали идентичный ответ и одинаковые оценки (0.297 / 0.275 / 0.270 / 0.186). Целостность хранилища: payload-хеш совпал, изменённых файлов нет, **0 LLM-вызовов, 0 записей**. Ограничения: документ написан мной и совпадает с K3 (проверен приоритет, не достоверность); разбор документа построчный по ключевым словам; проверка «документ новее памяти» не реализована; остаток `f632a54d` формально активен; ранжирование Mem0 между №2Б и №3 разошлось (0.236 против 0.297 на одном хранилище) — причина не изолирована. Актуализация без сервиса: документ в репозитории меняется тем же коммитом (git даёт аудит), обязательная «Дата пересмотра», `source` в записях указывает на документ, противоречия снимаются уже проверенным `update()` в той же сессии.
