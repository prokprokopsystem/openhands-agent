# Среда видеостудии: FFmpeg / ffprobe и хранилище

Каталог развёрнут на mini-server в `/home/igor/video-studio`. Имя `stage-2a` —
историческое: здесь лежит среда этапа 2а и подготовленная схема хранения этапа
2в. Рендер не входит в этот каталог: здесь только среда и правила.

## Состав

| `tests/run-tests.sh` | стенд на подставных устройстве и командах: проверяет, что примерка ничего не исполняет, а отказы срабатывают |
| `host/setup-storage.sh` | резервный вариант на loop-образе; без `--apply` только примерка |

| `host/remove-storage.sh` | демонтаж с резервной копией `fstab`; данные удаляются только с `--delete-image` и только для обычного файла-образа |

## Правила для привилегированных скриптов

1. Примерка ничего не исполняет. Каждый скрипт с `--apply` печатает план и
   запускает шаги только при `--apply`; одна и та же строка не выполняется
   дважды.
2. Пути заданы константами. `MOUNT`, `IMAGE`, `DEV`, `FSTAB` не читаются из
   окружения: у скрипта с `mkfs` и `umount` подмена пути означала бы работу не
   с тем устройством.
3. Откат срабатывает на любом выходе. Ловушка стоит на `EXIT`, а не на `ERR`:
   ошибка в условии вида `cmd || die` в `ERR` не попадает.
4. Размер сверяется одним модулем `size-check.sh` с абсолютным допуском 1 GiB —
   и в образе, и на хосте.
5. `--fill` запрещён на рабочем SSD: он пишет до `ENOSPC`. Проверка предела
   выполняется на отдельном маленьком хранилище и требует файла
   `.fill-test-ok`.
6. Неинтерактивность. `mkfs.ext4` получает stdin от `/dev/null` и никогда не
   вызывается с `-F`. Остатки прежней файловой системы стираются `wipefs -a`
   только по разделу своего диска, после проверки адресации и занятости, и с
   контролем `blkid -p` после стирания. Если разметка или `ext4` уже созданы,
   повторные `sgdisk`, `wipefs` и `mkfs` не выполняются.
7. Вывод утилит разбирается по явно заданным столбцам, а не по формату по
   умолчанию: `wipefs --no-act --noheadings --output TYPE`. Ненулевой код
   возврата любой из проверок означает отказ, а не «сигнатур нет».

Проверить эти правила без реального диска: `./tests/run-tests.sh`. Стенд
подменяет устройство, `mkfs`, `mount` и `df`, поэтому привилегированных
операций не требует.

## Два режима

### tmpfs — этап 2а, работает сейчас

```
ffmpeg --> tmpfs /out (1 GiB, предел ядра) --> tar-поток --> ./out на диске
```

1. Каталог хоста **не смонтирован** в контейнер: у процесса монтажа нет цели для
   записи на диск — ни в `/srv`, ни в Paperless, ни в Nextcloud.
2. Всё, что создаёт ffmpeg, попадает в `tmpfs /out` 1 GiB. Предел задаёт ядро:
   при переполнении запись прекращается.
3. Дополнительно действует `RLIMIT_FSIZE` = 1 GiB на один файл.
4. Публикация — поток `tar` из `tmpfs` в `./out`; объём ограничен содержимым
   `tmpfs`.
5. `run-render.sh` отказывается работать, если на разделе меньше 60 GiB свободно
   или `out/` занят более 15 GiB.

### disk — этап 2в, готов к включению после согласования

```
ffmpeg --> /srv/video-studio-data (ext4 40 GiB) --> готовый файл сразу на месте
```

Предел задаёт файловая система: при переполнении запись останавливается с
`ENOSPC`. Ограничение действует на сумму файлов, а не на один файл. Подробный
разбор схем, риски и точные команды — `../План-хранения-2026-11-15.md`.

## Ограда

Перед каждым запуском ffmpeg проверяется:

| Режим | Что проверяется |
|---|---|
| `tmpfs` | `/out` — `tmpfs`, размер не больше 1 GiB, запись возможна |
| `disk` | `/out` — не `tmpfs` и не слой контейнера; размер совпадает с маркером `/storage/.storage-size-gib` (±5%), запись возможна; `/scratch` на той же файловой системе |

Отказ всегда с кодом 78, ffmpeg не запускается. Проверены отказы: bind общего
раздела (935 GiB) без маркера и с поддельным маркером «40 GiB», `tmpfs`, ext4
размером 1 GiB, read-only каталог, отсутствие хранилища.

**Честная граница.** В режиме `tmpfs` жёсткие пределы — это `tmpfs` и
`RLIMIT_FSIZE`, а проверки объёма `out/` — контроль, не квота. В режиме `disk`
жёсткий предел даёт файловая система 40 GiB. Квоты на Docker-образы и build cache
нет: они лежат на общем разделе, и `check-docker-space.sh` только измеряет их
перед установкой HyperFrames.

## Запуск

```bash
cd /home/igor/video-studio

# режим tmpfs, как сейчас
./scripts/run-render.sh -i /work/in.mp4 -c:v libx264 -preset veryfast /out/out.mp4

# режим disk, после создания хранилища
MODE=disk ./scripts/run-render.sh -i /work/in.mp4 -c:v libx264 -preset veryfast /out/out.mp4
```

Входные файлы: `work/` в режиме `tmpfs`, `/srv/video-studio-data/in` в режиме
`disk`. Оба монтируются только на чтение.

Проверки:

```bash
./scripts/verify.sh                      # режим tmpfs
./scripts/verify-storage.sh              # хранилище, без заполнения
./scripts/verify-storage.sh --fill       # только на маленьком тестовом хранилище
./scripts/check-docker-space.sh          # бюджет перед HyperFrames
./host/check-storage.sh                  # состояние хранилища
```

`verify-storage.sh` работает в собственном проекте compose
`video-studio-disk-check`, поэтому его `down` не может задеть ни `studio` из
`compose.yaml`, ни тем более чужие сервисы. Состав остальных контейнеров
снимается до и после: расхождение считается провалом.

Каталог хранилища в `compose.disk.yaml` задаётся `STORAGE_ROOT` (по умолчанию
`/srv/video-studio-data`). Без этого `MOUNT=/mnt/storage-test ... --fill`
проверял бы тестовый образ, а заполнял рабочий SSD.

## Порядок включения режима disk

Выполняется только после отдельного разрешения на привилегированные операции.

```bash
cd /home/igor/video-studio

./host/setup-ssd-storage.sh                     # 1. примерка, ничего не меняет
sudo ./host/setup-ssd-storage.sh --apply --confirm-serial 24257G400264   # 2. разметить и смонтировать
./host/diagnose-storage.sh                      # 3. диагностика, только чтение
./scripts/verify-storage.sh                     # 4. базовые проверки
# 5. предел переполнения проверяется отдельно, на тестовом хранилище:
#    MOUNT=/mnt/storage-test ./scripts/verify-storage.sh --fill
#    На рабочем SSD --fill запрещён и отклоняется до запуска контейнера.
docker compose -f compose.disk.yaml up -d studio-disk   # 6. включить сервис
MODE=disk ./scripts/run-render.sh ... /out/probe.mp4     # 7. пробный запуск
```

Для loop-варианта вместо шага 2: `sudo ./host/setup-storage.sh --apply`.

Откат: `docker compose -f compose.disk.yaml down`, затем
`sudo ./host/remove-storage.sh --apply`. Данные на разделе SSD скрипт не стирает.
Примерка того же скрипта без `--apply` печатает план и ничего не исполняет.
Режим `tmpfs` при этом остаётся рабочим всё время — `compose.yaml` не меняется.

## Проверка дискового режима

Хранилище создано: `/dev/sdc1`, ext4, метка `VIDEO_STUDIO`, 926 GiB,
монтируется в `/srv/video-studio-data`, `srv-video\x2dstudio\x2ddata.mount`
active. Ничего из перечисленного ниже не форматирует и не размечает.

```bash
cd /home/igor/video-studio

./host/check-storage.sh          # 1. состояние, только чтение
./scripts/verify-storage.sh      # 2. базовые проверки, временный контейнер своего проекта
MODE=disk ./scripts/run-render.sh \
  -f lavfi -i testsrc=size=640x360:rate=25 -t 2 \
  -c:v libx264 -preset veryfast -y /out/probe.mp4     # 3. пробный рендер, около 200 КБ
ls -l /srv/video-studio-data/out/probe.mp4           # 4. файл дошёл до хранилища
rm -f /srv/video-studio-data/out/probe.mp4           # 5. убрать пробу
```

Шаг 3 пишет один короткий файл и проверяет весь путь: привязки томов, ограду с
квотой, `ffmpeg` в дисковом режиме. `lavfi` не требует входного файла, поэтому
ничего в `/work` не нужно.

`--fill` на рабочем SSD запрещён и отклоняется до запуска контейнера: тест
пишет до `ENOSPC`, а это 926 GiB записей и полное занятие места. Предел
переполнения проверяется на отдельном маленьком хранилище.

## Остановка и полное удаление

```bash
cd /home/igor/video-studio
docker compose down                 # остановить среду tmpfs, образ остаётся
docker compose -f compose.disk.yaml down   # остановить сервис disk
docker compose down --rmi local     # остановить и удалить образ
rm -rf /home/igor/video-studio      # удалить каталог
```

`docker compose down` не трогает образы, тома и сети других проектов. Общий
`docker prune` не нужен и не применяется.

## Технические особенности

- База `debian:bookworm-slim`, а не Alpine: бинарники BtbN собраны под glibc.
- `tmpfs /out` монтируется с режимом `1777`: этот runtime не принимает `uid`/`gid`
  в опциях tmpfs. В контейнере один пользователь.
- В режиме `tmpfs` контейнер живёт постоянно (`sleep infinity`), потому что tmpfs
  существует только пока контейнер запущен. В режиме `disk` это не нужно, но
  схема запуска та же.
- `docker cp` не видит `tmpfs` внутри контейнера, поэтому в режиме `tmpfs`
  публикация идёт потоком `tar`.
- `stat -f -c %T` не различает ext2/3/4 и печатает `ext2/ext3`, поэтому ограда в
  режиме `disk` проверяет отказ от `tmpfs`/`overlay` и размер, а не имя типа.
- Лицензия GPL-2.0-or-later: вариант `gpl` включает `libx264` и `libx265`.
  Использование локальное; распространение образа требует соблюдения GPL.
