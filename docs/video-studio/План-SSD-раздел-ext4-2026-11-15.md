# Схема хранения на SSD 1 ТБ: обычный раздел ext4 вместо LVM

**Дата:** 15.11.2026
**Основание:** [Issue #10](https://github.com/prokprokopsystem/openhands-agent/issues/10), решение сделать SanDisk Extreme SSD основным носителем видеостудии
**Режим:** только анализ и подготовка плана. Ни `sudo`, ни `mkfs`, ни `pvcreate`, ни изменения разделов, ни `mount`, ни правки `fstab` не выполнялись. PR #11 не слит.

## 1. Решение

**Один раздел GPT на весь диск + `ext4`, без LVM.** Причина: LVM не даёт ни
байта дополнительной ёмкости на выделенном диске, но добавляет слой, который
ломается иначе, чем файловая система, и усложняет перенос диска на другой
компьютер. Все требования из задачи выполняются и без него.

LVM остаётся оправданным только там, где нужен рост тома внутри одного
устройства. Здесь устройство выделенное и занимает 100% диска — расти некуда
ни в одной из схем.

## 2. Что в скриптах PR #11 рассчитано на loop-образ 40 GiB

Это главный риск, о котором вы спросили. Проверил каждый файл построчно.

зависит от носителя, хостовые скрипты писались под loop».

## 3. Сравнение: раздел ext4 против LVM

| Требование | Один раздел ext4 | LVM + ext4 |
|---|---|---|
| Физическая изоляция от системного диска | Полная: отдельное устройство, отдельный суперблок | Полная, но между диском и ФС появляется device-mapper |
| Использование ёмкости 1 ТБ | 931,5 GiB раздел, ≈927 GiB доступно | 931,5 GiB PV минус метаданные, ≈926 GiB доступно |
| Монтирование по UUID | `UUID=` из `blkid`, без промежуточных слоёв | `UUID=` работает, но нужен `lvm2` и активация VG |
| Запрет записи на `/` при отключении | Ограда + маркер, как в PR #11 | То же самое |
| Восстановление после обрыва USB | `umount -f`, `mount -a`, при нужде `e2fsck /dev/sdc1` | Дополнительно проверить, что VG собралась: `pvs`, `vgs`, `lvchange -ay` |
| Восстановление после ошибки ФС | `e2fsck` прямо на разделе | `e2fsck` на `/dev/mapper/…`, после `vgchange -ay` |
| Перезагрузка | одна запись `fstab`, один mount-unit | плюс юнит активации LVM, порядок запуска |
| Права FFmpeg и HyperFrames | владельцы и режимы каталогов, uid 10001 | идентично |
| Перенос на другой Linux | `mount UUID=… /mnt/x` на любой системе с ext4 | нужен пакет `lvm2`, иначе том не виден |
| Рост тома | невозможен без пересоздания раздела | `lvextend -r` онлайн |
| Сжатие | невозможно | возможно после размонтирования и `e2fsck -f` |
| Снимки | нет | возможны |
| Диагностика | `blkid`, `dumpe2fs`, `df` | плюс `pvs`, `vgs`, `lvs`, `dmsetup` |
| Число слоёв, которые могут отказать | 2: USB-мост, ФС | 3: USB-мост, LVM, ФС |

**Что даёт LVM:** только онлайн-рост и снимки.
**Что стоит LVM:** ещё один слой отказов на съёмной шине, обязательная
активация VG после каждого подключения, лишний пакет при переносе, ~1 GiB
ёмкости.

**Чего LVM здесь не решает:** диск занимает весь объём, свободного места для
роста нет ни в одной схеме. Если понадобится больше 927 GiB — нужен второй
диск, а не `lvextend`.

**Проверено на mini-server:** `lvm 2.03.31`, `use_devicesfile` в
`/etc/lvm/lvm.conf` закомментирован (значение `0`), `/etc/lvm/devices/`
отсутствует. То есть перенос не потребует `lvmdevices --adddev`, но пакет
`lvm2` на принимающей машине всё равно нужен.

## 4. Ёмкость: реальные числа

Расчёт сделан `mkfs.ext4 -n` на временном sparse-файле того же размера, файл
удалён. Ничего не форматировалось.

Диск: 1 953 459 617 секторов × 512 = 1 000 171 323 904 байт = 931,5 GiB.
Блоков по 4 KiB: 244 056 064.

| Вариант `mkfs` | Inode-таблица | Доступно по `df` |
|---|---|---|
| по умолчанию, `-m 5` | 61 014 016 inode = 14,6 GiB | ≈870 GiB (46,5 GiB отдано root-резерву) |
| `-m 0` | 61 014 016 inode = 14,6 GiB | ≈916 GiB |
| **`-m 0 -i 65536`** | **15 253 504 inode = 3,6 GiB** | **≈927 GiB** |
| `-m 0 -T largefile` | 953 344 inode = 0,2 GiB | ≈930 GiB, но всего 953 тыс. файлов |

**Выбор: `-m 0 -i 65536`.** Резерв для root не помогает: контейнер пишет от
uid 10001, и 5% резерва ему недоступны — они только уменьшают ёмкость на
46 GiB. Плотность inode 64 KiB на файл даёт 15,2 млн файлов: хватает и на
клипы, и на кадры HyperFrames, и на временные файлы. Вариант `largefile`
выигрывает ещё 3 GiB, но ограничивает хранилище 953 тыс. файлов — для монтажа
это мало.

Итог: **≈927 GiB доступно, 99,5% от номинала**. LVM дал бы ≈926 GiB.

## 5. Итоговая схема

```
/dev/sdc                        SanDisk Extreme 55AE, serial 24257G400264
└─/dev/sdc1                     GPT, тип 8300, метка VIDEO_STUDIO, 100% диска
                                ext4, VIDEO_STUDIO, -m 0 -i 65536
   /srv/video-studio-data       монтирование по UUID, nofail
   ├─ in/      → /work     ro   исходники
   ├─ out/     → /out      rw   готовые рендеры
   ├─ tmp/     → /scratch  rw   временные файлы ffmpeg и HyperFrames
   ├─ archive/ → —              архив, в контейнер не монтируется
   └─ .storage-size-gib    ro   маркер размера для ограды
```

Строка `fstab`:

```
UUID=<UUID раздела> /srv/video-studio-data ext4 rw,nosuid,nodev,noexec,noatime,nofail,errors=remount-ro,x-systemd.device-timeout=30s 0 0
```

Почему именно так:

- **`UUID=`, а не `/dev/sdc1`.** С двумя USB-дисками буквы после перезагрузки
  меняются местами. Это новый риск, которого не было с одним диском.
- **`nofail` и таймаут 30 с.** Без SSD сервер загрузится. `fstab` не станет
  точкой отказа для AMNESIA, Paperless и Nextcloud.
- **`noatime`.** Видео читается большими файлами; без `atime` меньше записи
  метаданных, для USB это заметно.
- **`nodev`, `nosuid`, `noexec`.** На этом разделе только данные. Такой же
  набор стоит на диске резервных копий.
- **`errors=remount-ro`.** Явно, хотя это и значение по умолчанию: при ошибке
  ввода-вывода ФС уходит в режим только чтения, ffmpeg получает ошибку и
  завершается, а не пишет дальше в повреждённую ФС.
- **`0 0` — без `fsck` при загрузке.** Проверка 927 GiB на USB может идти
  минутами и задержать старт. Журнал ext4 восстанавливается при монтировании
  сам; при реальных ошибках `mount` откажет, ограда не пустит рендер, а
  `e2fsck` запускается вручную. Для диска с данными, которые всегда можно
  пересоздать, это правильный компромисс.
- **`discard` в опциях не ставим.** Онлайн-TRIM на USB добавляет задержки.
  В системе уже активен `fstrim.timer` — еженедельная обрезка лучше.

## 6. Права доступа

| Каталог | Владелец | Режим | Кто пишет |
|---|---|---|---|
| `in/` | `igor`, группа `videostudio` (gid 10001) | `2775` | igor кладёт исходники, контейнер читает |
| `out/` | `10001:10001` → группа `videostudio` | `2775` | контейнер пишет, igor читает и удаляет |
| `tmp/` | `10001:10001` | `2770` | только контейнер |
| `archive/` | `10001:10001` | `2770` | контейнер |

Группа `videostudio` с **фиксированным gid 10001** нужна, чтобы uid 10001 в
контейнере и пользователь igor на хосте работали с одними каталогами без
`sudo`. Это единственная причина её создавать; если не нужен общий доступ к
`out/`, можно оставить `chown 10001:10001` и режим `0755` — igor сможет
читать результаты, а удалять будет через контейнер или `sudo`.

Изменение группы применится к igor только в новом сеансе (`newgrp videostudio`
или повторный вход).

## 7. Проверка, что выбрано верное устройство

Обязательный шаг перед любой разрушительной командой. Работает без root.

```bash
EXPECT_SERIAL=24257G400264
DEV=/dev/disk/by-id/usb-SanDisk_Extreme_55AE_323432353747343030323634-0:0

# 1. символьная ссылка ведёт туда, куда думаем
readlink -f "$DEV"                    # ожидается /dev/sdc

# 2. серийный номер совпадает
lsblk -dno SERIAL "$DEV"              # ожидается 24257G400264

# 3. это не системный диск и не диск резервных копий
lsblk -dno NAME,SIZE,TRAN,MODEL "$DEV"
#   sdc  931.5G  usb  Extreme 55AE       — верно
#   sda  953.9G  sata SSDPR-CX400-01T-   — СТОП
#   sdb  238.5G  usb  SanDisk SD9TB8W    — СТОП

# 4. на устройстве нет смонтированных файловых систем
findmnt -S "$DEV" -o SOURCE,TARGET     # пусто

# 5. нет держателей устройства
grep -c "^$DEV" /proc/mounts           # 0

# 6. жёсткая проверка одним условием
[ "$(lsblk -dno SERIAL "$DEV")" = "$EXPECT_SERIAL" ] \
  && echo "УСТРОЙСТВО ПОДТВЕРЖДЕНО" \
  || { echo "СТОП: не тот диск"; exit 1; }
```

Если любая проверка не совпала — остановиться. Все разрушительные команды
ниже указывают `$DEV`, а не `/dev/sdc`.

## 8. План настройки

### Шаг 0. Проверка устройства (без root)

Команды из §7. Записываю вывод в протокол.

### Шаг 1. Инвентаризация содержимого NTFS (root, только чтение)

Нужно отдельное разрешение. Без этого шага форматировать нельзя: на диске
раздел NTFS с меткой `Локальный диск`, MBR и флаг загрузки — он мог быть
системным в Windows.

```bash
sudo mkdir -p /mnt/ssd-inventory
sudo ntfs-3g -o ro,noload /dev/disk/by-id/usb-SanDisk_Extreme_55AE_323432353747343030323634-0:0-part1 /mnt/ssd-inventory
df -h /mnt/ssd-inventory
ls -la /mnt/ssd-inventory
du -xhd1 /mnt/ssd-inventory 2>/dev/null | sort -h | tail -20
sudo umount /mnt/ssd-inventory
```

`ntfs-3g`, а не ядерный драйвер: модуль `ntfs3` в системе есть, но монтирование
через FUSE предсказуемее и не пытается ничего писать. `noload` запрещает
воспроизведение журнала NTFS — важно, чтобы чтение осталось чтением.

Результат показывается вам. **Дальше — только после явного подтверждения, что
содержимое не нужно.**

### Шаг 2. Разметка и файловая система (root, разрушительно)

```bash
EXPECT_SERIAL=24257G400264
DEV=/dev/disk/by-id/usb-SanDisk_Extreme_55AE_323432353747343030323634-0:0
[ "$(lsblk -dno SERIAL "$DEV")" = "$EXPECT_SERIAL" ] || { echo "СТОП"; exit 1; }

sudo umount /mnt/ssd-inventory 2>/dev/null || true
sudo sgdisk --zap-all "$DEV"
sudo partprobe "$DEV"; sudo udevadm settle
sudo sgdisk --new=1:0:0 --typecode=1:8300 --change-name=1:VIDEO_STUDIO "$DEV"
sudo partprobe "$DEV"; sudo udevadm settle

lsblk -o NAME,SIZE,TYPE,PARTTYPENAME "$DEV"
# ожидается: sdc 931.5G disk, sdc1 931.5G part, Linux filesystem

sudo mkfs.ext4 -m 0 -i 65536 -L VIDEO_STUDIO "${DEV}-part1"
sudo blkid "${DEV}-part1"        # записать UUID
```

`sgdisk`, а не `parted`: одна команда на раздел, явный тип, понятный откат.
Таблица GPT, а не MBR: контрольные суммы, резервная копия таблицы в конце
диска, нет ограничения 2 TiB.

### Шаг 3. Монтирование и `fstab` (root)

```bash
UUID=$(sudo blkid -s UUID -o value "${DEV}-part1")
sudo mkdir -p /srv/video-studio-data
sudo cp -a /etc/fstab "/etc/fstab.bak-$(date +%Y%m%d-%H%M%S)"

printf 'UUID=%s /srv/video-studio-data ext4 rw,nosuid,nodev,noexec,noatime,nofail,errors=remount-ro,x-systemd.device-timeout=30s 0 0\n' "$UUID" \
  | sudo tee -a /etc/fstab

sudo systemctl daemon-reload
sudo mount /srv/video-studio-data
findmnt -no SOURCE,FSTYPE,SIZE,OPTIONS /srv/video-studio-data
df -h /srv/video-studio-data
```

Проверка, что монтирование переживёт перезагрузку, без перезагрузки:

```bash
sudo umount /srv/video-studio-data
sudo systemctl daemon-reload
sudo mount -a
findmnt -no TARGET,SIZE /srv/video-studio-data
```

### Шаг 4. Каталоги, права, маркер (root)

```bash
MOUNT=/srv/video-studio-data
sudo install -d -m 2775 "$MOUNT/in" "$MOUNT/out" "$MOUNT/archive"
sudo install -d -m 2770 "$MOUNT/tmp"

# группа с gid контейнера — по желанию, см. §6
sudo groupadd -g 10001 videostudio 2>/dev/null || true
sudo chown igor:10001 "$MOUNT/in"
sudo chown 10001:10001 "$MOUNT/out" "$MOUNT/tmp" "$MOUNT/archive"

# маркер из фактического размера, а не из номинала диска
size_gib=$(( $(df -Pk --output=size "$MOUNT" | awk 'NR==2{print $1}') / 1048576 ))
printf '%s\n' "$size_gib" | sudo tee "$MOUNT/.storage-size-gib"
sudo chmod 0444 "$MOUNT/.storage-size-gib"
```

Маркер считается из `df`, а не из 931,5 GiB: ограда сверяет размер с
объявленным, и точное значение убирает догадки. Ожидается 926–927.

### Шаг 6. Пробный рендер и защита от записи на `/`

```bash

MODE=disk ./scripts/run-render.sh -f lavfi -i testsrc=size=640x360:rate=25 -t 5 \

# 2. результат удалить, тест не хранить

sudo mount /srv/video-studio-data
```

Пункт 4 — прямая проверка того, о чём вы спросили: при потере монтирования
запись не уходит на `/`.

### Шаг 7. TRIM

Если ответ `discard operation not supported` — мост USB не пропускает TRIM.
Это не ошибка настройки, но знать полезно: износ будет распределяться хуже.

## 9. Почему запись не уйдёт на системный раздел

Пять независимых уровней, все проверены опытом на образе 15.11.2026:

1. **`run-render.sh` проверяет `findmnt` до запуска контейнера.** Нет
   монтирования — отказ, контейнер не поднимается.
2. **Ограда — это `ENTRYPOINT` образа** (`Dockerfile`, строка 41). Даже прямой
   `docker run` с аргументами проходит через неё, а не только вызов из скрипта.
3. **Маркер на самой файловой системе.** Если Docker создаст пустой каталог на
   `/`, маркера там нет → `ОГРАДА: нет маркера … /out не указывает на
   хранилище`, код 78.
4. **Сверка размера.** Подделанный маркер не помогает: 936 GiB системного
   раздела не совпадут с объявленными 927 GiB → отказ. Опыт: маркер «40»
   против 935 GiB дал отказ.
5. **`errors=remount-ro`.** При обрыве USB во время рендера ФС уходит в только
   чтение, ffmpeg получает ошибку ввода-вывода и завершается. Bind-монтирование
   контейнера указывает на прежнюю файловую систему, а не на `/`.

**Чего сознательно не делаем:** `RequiresMountsFor=/srv/video-studio-data` в
drop-in для `docker.service`. Это гарантировало бы монтирование до Docker, но
при отключённом SSD Docker не запустился бы вовсе — вместе с Paperless,
Nextcloud и AMNESIA. Изоляция сервисов важнее, поэтому защита стоит на уровне
рабочего контейнера.

## 10. Действия при ошибках

| Сценарий | Признак | Что делать |
|---|---|---|
| Диск не виден | `lsblk` без `sdc` | Проверить кабель и порт, `dmesg -T \| tail`. Порт `2-2` работал; другой порт может быть USB 2.0 |
| Не тот серийный номер | проверка §7 не прошла | **Остановиться.** Ничего не форматировать |
| `sgdisk` не может открыть устройство | `Device or resource busy` | `sudo umount` всего с диска, `grep sdc /proc/mounts`, `sudo partprobe` |
| `mkfs` прервался | ошибка записи | Повторить `mkfs`. Данных на разделе ещё нет |
| `mount`: `wrong fs type` | нет модуля или пустой суперблок | `sudo blkid`, `dmesg -T \| tail` |
| `mount`: `Structure needs cleaning` | журнал или ошибки ФС | `sudo e2fsck -f -y /dev/sdc1`, затем `mount` |
| `mount`: `already mounted or busy` | держатели | `sudo fuser -vm /srv/video-studio-data`, затем `umount` |
| Обрыв USB во время рендера | `I/O error`, `dmesg`: `uas_eh_abort_handler` | ffmpeg падает сам. `findmnt` покажет мёртвое монтирование; `sudo umount -f` или `-l`, переподключить кабель, `sudo mount /srv/video-studio-data` |
| После перезагрузки не смонтировано | `findmnt` пусто | `systemctl status "srv-video\\x2dstudio\\x2ddata.mount"`, `sudo journalctl -b \| grep video-studio`, проверить UUID: `sudo blkid` |
| Диск стал `/dev/sdd` | `lsblk` | Ничего: монтирование по UUID. Только не использовать `/dev/sdX` в скриптах |
| Ошибка в `fstab` при загрузке | сервер загрузился, но без хранилища | `nofail` уже исключает блокировку; откат: `sudo cp /etc/fstab.bak-* /etc/fstab` |
| Хранилище заполнено | ffmpeg: `No space left on device` | Почистить `out/` и `archive/`, повторить. Лимит файла 20 GiB задан в `ulimits` |
| Ограда отказывает после настройки | код 78 | Сверить `df` и маркер: `cat /srv/video-studio-data/.storage-size-gib`, `df -BG /srv/video-studio-data`. После `resize2fs` маркер надо обновлять |

## 11. Отмена и перенос

**Демонтаж:**
```bash
cd /home/igor/video-studio && docker compose -f compose.disk.yaml down
sudo umount /srv/video-studio-data
sudo cp -a /etc/fstab "/etc/fstab.bak-$(date +%Y%m%d-%H%M%S)"
sudo sed -i '\#/srv/video-studio-data#d' /etc/fstab
sudo systemctl daemon-reload
```
Диск при этом цел, данные на месте.

**Перенос на другой Linux-компьютер:** подключить, `lsblk`, затем
`sudo mount UUID=<UUID> /mnt/video`. Никаких дополнительных пакетов не нужно —
это и есть главный довод против LVM.

**Полное стирание перед передачей диска:**
```bash
sudo umount /srv/video-studio-data
sudo wipefs -a /dev/sdc
sudo blkdiscard /dev/sdc        # если мост поддерживает TRIM
```

## 13. Что осталось непроверенным

- **Содержимое NTFS** — не читалось, разрешения не было.
- **SMART** — недоступен: `smartctl` не установлен, `udisks2` интерфейса
  `Drive.Ata` для USB-моста не даёт, чтение блочного устройства требует root.
- **Реальная скорость** — не измерялась: нужен root и запись.
- **Перегрев и питание** — при длинном рендере USB SSD может уходить в
  троттлинг. Проверяется только наблюдением за скоростью.
- **Модуль `ntfs3`** — в системе есть, но чтение NTFS планируется через
  `ntfs-3g` (FUSE), чтобы не зависеть от версии ядра.

## 14. Краткая рекомендация

1. Диск под видеостудию — **один раздел GPT на весь диск + `ext4`
   (`-m 0 -i 65536`)**, без LVM. Это проще, переносимо и даёт те же ≈927 GiB.
2. Монтирование — **по UUID** с `nofail`, `noatime`, `nodev`, `nosuid`,
   `noexec`, `errors=remount-ro`, `0 0`.
3. Сначала — **инвентаризация NTFS только для чтения** и явное подтверждение,
   что содержимое не нужно.
4. Скрипты PR #11 в текущем виде **не применять**: `setup`, `resize`, `remove`,
   `verify`, `check` рассчитаны на loop-образ и дадут ошибки. Рабочие —
   `guard.sh`, `run-render.sh`, `compose.disk.yaml`, `check-docker-space.sh`.
5. PR #11 не сливать до проверки на реальном разделе.
6. Диск `AMNESIA_BACKUP` не трогается ни на одном шаге.
