## 2. Что изменилось после первого отчёта

Первая версия обещала защиту диска, которой не было. Разбор показал три дефекта:

| Дефект | Как проявлялся | Исправление |
|---|---|---|
| Общий объём `out/` не ограничен | `ulimit -f` считает каждый файл отдельно | всё пишется в `tmpfs` 1 GiB — предел задаёт ядро |
| Проверку можно было обойти | `preflight.sh` вызывался вручную, прямой `docker compose run` его пропускал | `preflight.sh` удалён; проверки встроены в `run-render.sh` и в entrypoint образа |
| Контейнер мог писать на хост | каталог `./out` монтировался в режиме rw | монтирование убрано полностью |

Дополнительно найдено на практике:

- `docker cp` в этом runtime не видит `tmpfs` внутри контейнера и молча
  копирует пустоту, поэтому публикация переведена на поток `tar`;
- `tmpfs` исчезает при остановке контейнера, поэтому рабочий контейнер живёт
  постоянно, а рендеры идут через `docker exec`;
- режим `1777` у `/out` вынужденный: `uid`/`gid` в опциях `tmpfs` этот runtime
  не принимает.

### Доводка ограды после слияния PR #7

Первая версия ограды проверяла только тип файловой системы, поэтому её можно
было обмануть. Добавлено ещё две проверки и исправлена неудобная точка входа:

| Случай | Было | Стало |
|---|---|---|
| `/out` — bind большого `tmpfs` хоста | принято (7.8 GiB свободно) | отказ: размер больше 1 GiB |
| `/out` смонтирован read-only | принято, ошибка только при записи | отказ с кодом 78: недоступен для записи |
| `docker compose run studio -version` | уходило в `/bin/sleep` с непонятной ошибкой | ограда и нормальный ответ ffmpeg |

Ограда проверяет: тип `tmpfs`, размер не больше 1 GiB, возможность записи.
Все три отказа и штатный запуск проверены отдельно.

## 3. Как ограничен дисковый вывод

```
ffmpeg --> tmpfs /out (1 GiB) --> tar-поток --> ./out на диске хоста
```

**Жёсткие пределы, обеспеченные ядром:**

1. `tmpfs /out` = 1 GiB. Проверено попыткой записать 1.5 GiB:
   `File size limit exceeded`, файл остался ровно 1073741824 байт,
   `df` показал `1.0G / 1.0G / 0%`.
2. `RLIMIT_FSIZE` = 1 GiB на файл. Проверено в изолированном тесте:
   `tmpfs` 8 MiB остановил запись ровно на 8388608 байт.
3. Корневая ФС read-only, писать можно только в `/out` и `/tmp`.

**Контролируемые проверки, не квота:**

- `run-render.sh` требует ≥ 60 GiB свободных и `out/` ≤ 15 GiB;
- перед публикацией объём результата сверяется с остатком лимита;
- `verify.sh` подтверждает, что `/out` действительно `tmpfs` и не больше 1 GiB.

**Чего нет:** квоты файловой системы на `out/`. Она требует прав root на хосте
(project quota ext4 или отдельный LV). Настоящей квотой это не называется и не
заявляется. Отдельно: доступ к Docker равен правам root, поэтому оператор может
обойти любую проверку — это свойство доступа, а не конфигурации.

## 5. Минимальный технический рендер

Выполнен через `run-render.sh`, длительность 2 секунды, 640×360, тихий
синтетический звук. Художественным материалом не является.

| Параметр | Значение |
|---|---|
| Команда | `color=c=black:s=640x360:r=25:d=2` + `anullsrc=r=48000:cl=stereo` |
| Кодеки | `libx264 -preset veryfast`, `aac -b:a 96k` |
| Время | **0.61 с** на весь цикл, включая запуск и публикацию |
| Размер | 5274 байт |
| Проверка `ffprobe` | `format=mov,mp4`, `duration=2.000000`, 2 потока |
| Видео | `h264`, High, `yuv420p`, 640×360, 25/1, 50 кадров |
| Аудио | `aac`, LC, 48000 Гц, 2 канала, 95 кадров |
| Целостность | md5 хоста и контейнера совпал: `c73e309f6df2873e129b4799c5654c6e` |

Тестовый файл удалён после фиксации измерений; `out/` пуст. Повторный запуск
дал тот же md5, то есть результат воспроизводим.

Проверены отказы: недостаточно свободного места, нулевой остаток лимита,
запуск без аргументов. Все три завершаются отказом без записи в `out/`.
