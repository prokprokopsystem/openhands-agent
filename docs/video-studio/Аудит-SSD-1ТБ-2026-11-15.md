# Аудит внешнего SSD 1 ТБ (SanDisk Extreme Portable)

**Дата:** 15.11.2026, 12:42–12:50 UTC
**Основание:** [Issue #10](https://github.com/prokprokopsystem/openhands-agent/issues/10), уточнение пользователя о подключённом SSD 1 ТБ
**Режим:** строго чтение. Ничего не форматировалось, не монтировалось, `fstab` не правился, файлы не удалялись, `sudo` не выполнялся.

## 1. Итог

Диск виден, это **новое устройство**, не пересекающееся с системным диском и с
`AMNESIA_BACKUP`. Подключён по USB 3.0 с **UASP** — это лучше, чем у диска
резервных копий. Ёмкость 931,5 GiB.

Три вещи требуют решения до любой подготовки:

1. **Свободное место неизвестно**, содержимое не проверено: раздел `NTFS` с меткой
   `Локальный диск`, таблица разделов `MBR` с флагом загрузки. Читать NTFS без
   монтирования нельзя (нужен root), поэтому «диск пуст» я подтвердить не могу.
2. **SMART недоступен** — `smartctl` не установлен, установка запрещена условиями.
3. Диск уже один раз отключался в журнале (12:42:33 → 12:42:47), причину отличить
   от ручного переподключения нельзя.

Рекомендация: SSD — правильное место для видеостудии, но не NTFS. Перевести его в
`LVM` + `ext4` **после** инвентаризации содержимого. План PR #11 при этом не
выбрасывается: контейнерная часть остаётся той же, меняется только подготовка
носителя на хосте.

## 5. SMART

**Недоступен, ни одного показателя получить не удалось.**

| Способ | Результат |
|---|---|
| `smartctl` | не установлен (`/usr/sbin/smartctl`, `/usr/bin/smartctl` отсутствуют), установка запрещена условиями |
| `udisks2` (`Drive.Ata`) | интерфейса нет: у USB-моста SMART не проброшен, свойств `Smart*` — 0 |
| `parted`, `fdisk`, `ntfsinfo`, `dumpe2fs` | `Permission denied` — чтение блочного устройства только для root |

Косвенно: `rotational=0`, ошибок ввода-вывода за всё время журнала нет, кэш
включён, `Write Protect is off`. Это говорит лишь о том, что диск отвечает.
Износ ячеек, переназначенные сектора, температура и число отработанных часов
неизвестны.

Если понадобится: `smartctl -d sat -a /dev/sdc` может сработать через мост, но
требует установки пакета и root — отдельное согласование.

## 6. Свободное место и содержимое

| Что | Значение |
|---|---|
| Размер раздела | 931,5 GiB |
| Занято / свободно | **неизвестно** |
| Причина | NTFS не читается без монтирования, а монтирование запрещено условиями |

`lsblk` показывает `FSSIZE`, `FSUSED`, `FSUSE%`, `FSAVAIL` пустыми — libblkid без
доступа к устройству их не вычисляет.

Метка `Локальный диск` — стандартная для Windows. С учётом MBR и флага загрузки
раздел мог быть системным или содержать пользовательские данные. **Пока
содержимое не проверено, считать диск непустым.**

## 7. Как организовать рабочее хранилище

### 7.1 Почему NTFS не подходит

| Свойство NTFS | Последствие для FFmpeg и HyperFrames |
|---|---|
| Нет владельцев и прав POSIX | контейнер пишет от uid 10001, согласование прав превращается в костыли |
| Нет жёсткой квоты | Issue #10 требует предела, NTFS его не даёт |
| `ntfs-3g` в пользовательском пространстве | каждая операция через FUSE, для тысяч кадров это заметная потеря |
| Регистронезависимость | `Clip.MP4` и `clip.mp4` — один файл, скрипты ломаются |
| Нет жёстких ссылок | ротация и архивирование усложняются |
| `fsync`/`rename` семантика отличается | атомарная публикация результата ненадёжна |

### 7.2 Предлагаемая схема

`LVM` на всём SSD, один логический том `ext4` под видеостудию:

```
pvcreate /dev/sdc
vgcreate video-vg /dev/sdc
lvcreate -L 850G -n video-data video-vg
mkfs.ext4 -m 0 -L VIDEO_STUDIO /dev/video-vg/video-data
```

Монтирование в ту же точку, что в PR #11:

```
UUID=<новый UUID> /srv/video-studio-data ext4 defaults,nofail,nodev,nosuid,noatime,x-systemd.device-timeout=30s 0 2
```

Раскладка внутри — без изменений относительно PR #11:

```
/srv/video-studio-data/in      -> /work     ro   исходники
/srv/video-studio-data/out     -> /out      rw   готовые рендеры
/srv/video-studio-data/tmp     -> /scratch  rw   временные файлы
/srv/video-studio-data         -> /storage  ro   маркер .storage-size-gib = 850
```

**Почему LVM, а не раздел на 850 GiB:** хвост после текущего раздела — 2,7 MiB,
расширять нечего. Пересоздавать таблицу разделов на устройстве с неизвестным
содержимым незачем. `lvextend -r` увеличивает том без размонтирования, а в
хранилище остаётся 81 GiB нераспределённого места под рост.

**Почему не project quota:** пакет `quota` не установлен, а подкаталоги можно
ограничить позже, не рискуя данными: включение `project` на свежем `ext4`
безопасно, на диске с копиями — нет. Сейчас предел даёт сам том.

**Жёсткий предел:** размер логического тома. Переполнение даёт `ENOSPC`,
ограничение действует на сумму файлов, а не на отдельный файл. Та же природа
предела, что у loop-образа, но без файла-контейнера.

**Что остаётся от PR #11:** `compose.disk.yaml`, `guard.sh` в режиме `disk`,
`run-render.sh` с `MODE=disk`, `verify-storage.sh`, `check-docker-space.sh`. Меняется
только подготовка носителя на хосте: вместо `fallocate` + loop — `pvcreate` +
`lvcreate`.

### 7.3 Защита от записи на системный диск при отключении SSD

Пять уровней, все без изменений относительно PR #11:

1. **Монтирование по UUID, не по `/dev/sdc`.** С двумя USB-дисками буквы `sdb`
   и `sdc` после перезагрузки могут поменяться местами — это реальный риск,
   которого не было с одним внешним диском.
2. **`nofail` + `x-systemd.device-timeout=30s`.** Без SSD сервер загрузится, а не
   зависнет на 90 секунд.
3. **Проверка `findmnt` в `run-render.sh` до старта контейнера.** Нет
   монтирования — отказ, контейнер не поднимается.
4. **Маркер `.storage-size-gib` на самой файловой системе.** Если Docker создаст
   пустой каталог-источник на `/`, то `/out` окажется на разделе с 936 GiB: маркера
   там нет — `ОГРАДА: нет маркера … /out не указывает на хранилище`, код 78.
   Поддельный маркер тоже не помогает: размер сверяется с объявленным.
   Опыт 15.11.2026: маркер «40» против 935 GiB → `935 GiB не совпадает с
   объявленными 40 GiB`. С SSD будет то же самое: 936 GiB против 850 GiB.
5. **`errors=remount-ro` в ext4 по умолчанию.** При отключении посреди рендера
   файловая система уходит в режим только чтения, ffmpeg получает ошибку и
   завершается. Bind-монтирование контейнера указывает на прежнюю файловую
   систему, поэтому молчаливого перенаправления на `/` не происходит.

Дополнительно стоит сделать при подготовке: убедиться, что каталог
`/srv/video-studio-data` до монтирования пуст, и проверять это в
`run-render.sh` — непустой каталог при отсутствии монтирования означает
осиротевшие данные.

## 8. Сравнение с loop-образом 40 GiB на системном диске (PR #11)

| Критерий | Loop 40 GiB на `sda` | LV 850 GiB на SSD |
|---|---|---|
| Объём | 40 GiB | **850 GiB** |
| Природа предела | файловая система внутри файла | логический том |
| Пропускная способность | SATA ~500 МБ/с, прямой доступ | USB 3.0 + UASP ~400 МБ/с, выше нагрузка на CPU |
| Накладные расходы | loop-слой ~5–10%, двойная буферизация | нет |
| Занятие системного диска | 40 GiB из 848 | **0** |
| Устойчивость подключения | внутренний SATA, не отключается | кабель, питание, случайное извлечение |
| SMART | доступен на `sda` | недоступен без `smartctl` и root |
| Отказ носителя | теряется 40 GiB видеоданных, 848 GiB системы целы | теряются все видеоданные; резервные копии на `sdb` не затронуты |
| Соседство с бэкапами | нет | нет (в отличие от варианта с `sdb`) |
| Расширение | `truncate` + `resize2fs`, без размонтирования | `lvextend -r`, без размонтирования |
| Удаление | удалить файл | стереть том, вернуть диск |
| Резервная копия видео | 40 GiB легко скопировать | 850 GiB копировать дорого, нужен план |
| Риск для production | минимальный | минимальный |

**Что даёт SSD:** 21-кратный объём, освобождение системного диска, отсутствие
loop-слоя, отдельное устройство — сбой видео не затрагивает систему.

**Что теряет:** съёмная шина, недоступный SMART, ниже пропускная способность,
дороже резервное копирование, и на нём лежит NTFS с неизвестным содержимым,
которое придётся осознанно уничтожить.

## 9. Рекомендация

1. **Видеостудию разместить на SSD**, но не на NTFS — перевести в `LVM` + `ext4`,
   том 850 GiB, точка `/srv/video-studio-data`. Предел даёт том, контейнерная
   часть PR #11 не меняется.
2. **До форматирования — инвентаризация.** Нужно ваше разрешение на монтирование
   `sdc1` только для чтения (`udisksctl mount -b /dev/sdc1 --options ro` либо
   `sudo mount -o ro`). Без этого я не могу сказать, есть ли на диске данные и
   сколько занято. Уничтожать NTFS вслепую нельзя.
3. **PR #11 оставить как есть** и не сливать до подготовки SSD. Loop-схема — рабочий
   запасной вариант, её скрипты остаются в репозитории; в документации схема с SSD
   станет основной, loop — резервной.
4. **Отдельно согласовать** установку `smartmontools` для проверки здоровья SSD —
   без неё состояние накопителя остаётся неизвестным.
5. **Порядок подготовки SSD** (после согласования, всё с root):
   инвентаризация → решение о судьбе данных → `pvcreate`/`vgcreate`/`lvcreate` →
   `mkfs.ext4` → `fstab` по UUID с резервной копией → `mount` → каталоги `in`,
   `out`, `tmp`, `archive` → маркер `850` → `verify-storage.sh --fill` →
   рендер в режиме `disk` → удаление тестового результата.
6. **Пока подготовка не выполнена**, сервис работает в режиме `tmpfs` 1 GiB, как
   сейчас. Ничего не сломано.
