## 3. Пункт 2: инвентаризация NTFS — остановлено

Монтирование только для чтения **выполнить не удалось**, и это честный
результат, а не сбой:

```
sudo -n true                 → sudo: interactive authentication is required
sudo -n -l                   → (ALL : ALL) ALL, NOPASSWD только для
                               /usr/local/sbin/codex-mini-server-admin …
udisksctl mount -b /dev/sdc1 --options ro
                             → polkit: нет агента аутентификации
                               (NotAuthorizedCanObtain)
ntfsinfo /dev/sdc1           → Permission denied
ls -l /dev/sdc1              → brw-rw---- root:disk
```

`igor` в группе `disk` не состоит, а добавлять себя в неё — привилегированное
изменение, которое запрещено условиями. Обходных путей не искал.

**Следствие:** содержимое и свободное место NTFS неизвестны. Форматирование
остаётся неразрешённым. Чтобы двинуться дальше, нужно одно из двух:

- интерактивный сеанс с паролем root;
- либо вы сами выполняете:
  ```bash
  sudo mkdir -p /mnt/ssd-inventory
  sudo ntfs-3g -o ro,noload /dev/disk/by-id/usb-SanDisk_Extreme_55AE_323432353747343030323634-0:0-part1 /mnt/ssd-inventory
  df -h /mnt/ssd-inventory
  sudo du -xhd1 /mnt/ssd-inventory | sort -h | tail -20
  sudo umount /mnt/ssd-inventory
  ```

## 4. Найденная ошибка в моём скрипте

При проверке `--apply` без root обнаружилось, что установочный скрипт
**исполнил `sgdisk --zap-all`**, хотя должен был отказать. Причина: шаг «План»
вызывал функцию `run`, которая при `--apply` не печатает команду, а выполняет
её. Порядок был такой: план (уже исполнение) → проверка root → применение
(исполнение второй раз). Под root это дало бы двойной `mkfs` и две строки в
`/etc/fstab`.

Остановилось только потому, что у `igor` нет прав на запись в устройство:
`sgdisk` вернул `Problem opening for writing`, `MBR not overwritten, Error is 2`.

**Проверка диска после инцидента:**

| Параметр | До | После |
|---|---|---|
| Таблица разделов | `dos`, PTUUID `00007ab7` | `dos`, PTUUID `00007ab7` |
| Раздел | `sdc1`, начало 2048, 1 953 452 032 сектора | без изменений |
| ФС | NTFS, `Локальный диск` | NTFS, `Локальный диск` |

Диск не пострадал.

**Исправление:** введена функция `show`, которая только печатает, и шаг плана
переведён на неё. Проверка root перенесена в начало, до всех шагов. Повторный
тест `--apply` без root теперь даёт `ОТКАЗ: для --apply нужен root` и не
касается устройства.

## 5. Пункт 3: новый скрипт `host/setup-ssd-storage.sh`

Обязательные проверки перед любым действием:

1. путь `by-id` существует и является ссылкой;
2. ссылка ведёт на блочное устройство;
3. серийный номер равен `24257G400264`;
4. модель содержит `Extreme`;
5. шина `usb`;
6. объём не меньше 900 GiB;
7. это не `/dev/sda` по имени;
8. серийный номер не входит в список запрещённых (`4F0029407`, `181066800481`);
9. с устройства нет монтирований и оно не используется как swap;
10. точка монтирования не смонтирована и её каталог пуст.

Защита от повторного форматирования: если на устройстве есть метка
`VIDEO_STUDIO`, скрипт отказывает и требует `--reformat`. Если есть чужая
разметка, скрипт прямо предупреждает, что содержимое будет уничтожено.

Три условия для разрушительных действий: `--apply`, `--confirm-serial
24257G400264` и root. Без любого из них скрипт только печатает план. Перед
применением идентичность проверяется **повторно** — на случай переподключения
диска между примеркой и запуском.

## 7. Ужесточение ограды

Проверка маркера сверяла размер с допуском ±5%. На объёме 927 GiB это 46 GiB,
и корневой раздел 935 GiB **проходил** проверку: тест D показал, что подмена
каталога на `/` не ловилась, если маркер объявлял 927.

Допуск заменён на абсолютный: расхождение больше 1 GiB — отказ. Маркер

Выполняются только после разрешения и после инвентаризации NTFS.


**Шаг 1. Применение (root, уничтожает разметку NTFS):**

```bash
cd /home/igor/video-studio
```

## 10. Отказ, откат, перезагрузка, обрыв USB

### SSD отсутствует при загрузке

`nofail` и `x-systemd.device-timeout=30s` в `fstab` означают: сервер загрузится,
система дойдёт до multi-user, `docker.service` запустится, Paperless, Nextcloud
и AMNESIA поднимутся. Хранилище останется неcмонтированным.

Что будет с видеостудией: `run-render.sh` в режиме `disk` проверит `findmnt`,
не найдёт `ext4` и откажет с кодом 1. Контейнер не запустится вовсе. Записи на
`/` не произойдёт.

`RequiresMountsFor` в drop-in для `docker.service` **не добавляется**: при
отключённом SSD это не дало бы запуститься Docker, а вместе с ним легли бы
все остальные сервисы.

### Обрыв USB во время рендера

1. Ядро помечает устройство как отключённое, `ffmpeg` получает ошибку
   ввода-вывода и завершается.
2. Файловая система уходит в режим только чтения (`errors=remount-ro`), если
   ошибка дошла до суперблока.
3. `run-render.sh` останавливает контейнер по `trap` на выходе.
4. Восстановление — по шагам, без автоматики:
   ```bash
   ./host/diagnose-storage.sh          # факты: диск, монтирование, журнал
   sudo fuser -vm /srv/video-studio-data   # кто держит
   sudo umount /srv/video-studio-data      # обычное размонтирование
   # переподключить кабель, дождаться udev
   sudo mount /srv/video-studio-data
   ```

`umount -f` и `umount -l` **не являются способом восстановления по умолчанию**:
они выдёргивают файловую систему из-под процессов и оставляют непредсказуемое
состояние. Применяются только когда обычный `umount` не проходит и понятно,
почему.

### Ошибка файловой системы

Автоматический `e2fsck -y` не используется ни в скриптах, ни в загрузке:

- `fstab` содержит `0 0` — `fsck` при загрузке не запускается;
- журнал ext4 восстанавливается при монтировании сам;
- при серьёзной ошибке `mount` откажет, и ограда не пустит рендер;
- ручная проверка начинается с **чтения без исправлений**:
  ```bash
  sudo e2fsck -n /dev/disk/by-id/usb-SanDisk_Extreme_55AE_323432353747343030323634-0:0-part1
  ```
  `-n` отвечает «нет» на все вопросы и ничего не меняет. Только по результату
  решается, нужен ли ремонт, и до него сохраняется то, что читается.

Почему `fsck` при загрузке отключён: проверка 927 GiB по USB занимает минуты и
задержала бы старт всех сервисов ради данных, которые всегда можно пересоздать.

### Откат самой установки

```bash
cd /home/igor/video-studio
./host/remove-storage.sh                 # примерка
sudo ./host/remove-storage.sh --apply    # снять монтирование и запись fstab
```
Диск при этом остаётся размеченным и с данными. Если `mount` в установочном
скрипте не удался, он сам убирает свою строку из `fstab` и сообщает, что
разметка сделана, а данные не создавались.

Полный откат `fstab`:
```bash
sudo cp /etc/fstab.bak-<дата> /etc/fstab && sudo systemctl daemon-reload
```

### Диск стал `/dev/sdd`

Ничего делать не нужно: монтирование по UUID от буквы не зависит. Проверить:
`lsblk -o NAME,SERIAL,MOUNTPOINTS`.

## 11. Нерешённые риски

1. **Содержимое NTFS не проверено.** Форматирование запрещено до инвентаризации.
2. **SMART недоступен.** `smartctl` не установлен, `udisks2` не даёт интерфейс
   `Drive.Ata` для USB-моста, чтение блочного устройства требует root. Износ и
   температура SSD неизвестны.
3. **Скорость не измерена.** Нужен root и запись.
4. **Один обрыв в журнале.** 15.11 в 12:42:33 `Synchronize Cache(10) failed`,
   переподключение в 12:42:47. Причина не установлена: кабель, порт или
   ручное переподключение.
5. **Маркер — единственная защита внутри контейнера.** Если размер корневого
   раздела когда-нибудь совпадёт с объявленным в маркере с точностью до 1 GiB,
   ограда не отличит подмену. Внешняя проверка `findmnt` в `run-render.sh`
   остаётся главной.
6. **USB-мост и TRIM.** Поддержка TRIM не проверена: `fstrim` требует root, и
   мост может его не пропускать.
7. **Ветка `--confirm-serial` не исполнена в тесте.** В этой среде нет ни root
   без пароля, ни пользовательских пространств имён. Логика проверена чтением
   кода и порядком шагов.
8. **`verify-storage.sh --fill` не запускался.** Заполняет почти всё хранилище,
   безопасно только на реальном хранилище, которого пока нет.
