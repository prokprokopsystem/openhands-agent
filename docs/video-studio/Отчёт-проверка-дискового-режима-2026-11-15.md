# Проверка дискового режима Docker: тождество хранилища и изоляция контейнеров

Дата: 15 ноября 2026. Ветка `video-studio-disk-storage`, PR #11.
Основание: аудит `verify-storage.sh` после успешной установки SSD.

Ничего не форматировалось, не размечалось, `fstab` не менялся, рабочие
контейнеры не запускались и не останавливались. Проверки на хосте — только
чтение.

## 1. Состояние хранилища (измерено)

```
$ findmnt -no SOURCE,FSTYPE,SIZE,TARGET /srv/video-studio-data
/dev/sdc1 ext4 926.7G /srv/video-studio-data

$ disk=$(lsblk -no PKNAME /dev/sdc1 | head -1); lsblk -dno SERIAL,MODEL /dev/$disk
24257G400264 Extreme 55AE

$ df -Pk /srv/video-studio-data | awk 'NR==2{print $2}'
971718360 KiB  (= 926 GiB)

$ cat /srv/video-studio-data/.storage-size-gib
926

$ grep video-studio-data /etc/fstab
UUID=db167db5-f827-4e30-90d9-d3171d495f71 /srv/video-studio-data ext4 rw,nosuid,nodev,noexec,noatime,nofail,errors=remount-ro,x-systemd.device-timeout=30s 0 0

$ systemctl is-active srv-video\x2dstudio\x2ddata.mount
active
```

Маркер и файловая система сходятся: 926 GiB против 926 GiB, допуск 1 GiB не
израсходован.

## 2. Дефект 1: рабочий SSD отвергался по серийному номеру

Было:

```bash
[ "$source_serial" != "$PRODUCTION_SERIAL" ] \
  && ok "это не рабочий SSD видеостудии" \
  || bad "источник указывает на рабочий SSD видеостудии"
```

Условие писалось для проверок на тестовом образе, но применялось ко всем
точкам. На настоящем хранилище оно гарантированно давало провал: диск и
должен быть рабочим. То есть первая же правильная установка не проходила
проверку.

Стало — правило в две стороны:

| Точка монтирования | Серийный номер | Итог |
|---|---|---|
| `/srv/video-studio-data` | `24257G400264` | ПРОЙДЕНО, так и требуется |
| `/srv/video-studio-data` | другой или пустой | НЕ ПРОЙДЕНО: нужен рабочий SSD |
| любая другая | `24257G400264` | НЕ ПРОЙДЕНО: в рабочий SSD писать нельзя |
| любая другая | другой или пустой | ПРОЙДЕНО |

Вторая половина правила не косметика: проверка пишет пробы в `$MOUNT/out`, и на
тестовой точке она не должна попадать на рабочий диск.

## 3. Дефект 2: `MOUNT=…` не доходил до контейнера

`compose.disk.yaml` привязывал жёстко прописанные пути:

```yaml
- type: bind
  source: /srv/video-studio-data/out
  target: /out
```

`verify-storage.sh` при этом проверял `$MOUNT` с хоста. При
`MOUNT=/mnt/storage-test ./scripts/verify-storage.sh --fill` — а это ровно та
команда, которую рекомендовал README, — ворота `--fill` видели маленький
тестовый образ и разрешали заполнение, а контейнер писал в рабочий SSD до
`ENOSPC`. Это 926 GiB записей и полный износ диска.

Стало: каталог задаётся одним параметром.

```yaml
source: ${STORAGE_ROOT:-/srv/video-studio-data}/out
```

`verify-storage.sh` экспортирует `STORAGE_ROOT="$MOUNT"`, `run-render.sh` —
`STORAGE_ROOT="$STORAGE"`. Без переменной остаётся рабочий путь, поэтому
привычные команды из документации ничего не замечают. Проверено рендером
конфигурации:

```
$ STORAGE_ROOT=/tmp/x docker compose -f compose.disk.yaml config | grep -A1 'target: /out'
- type: bind
  source: /tmp/x/out
$ env -u STORAGE_ROOT docker compose -f compose.disk.yaml config | grep 'source: /srv'
  source: /srv/video-studio-data/out
```

## 4. Дефект 3: проверка могла задеть рабочий сервис `studio`

`compose.disk.yaml` и `compose.yaml` лежат в одном каталоге и оба объявляют
`name: video-studio`. Значит `docker compose -f compose.disk.yaml down` работал
в том же проекте, что и `studio` из tmpfs-схемы, и мог снять общую сеть
проекта. AMNESIA, Paperless, Nextcloud и OpenHands — другие проекты, до них
дело не доходило, но «не доходило» — не то же самое, что «не может».

Стало: у проверки своё имя проекта.

```bash
DC=(docker compose -f "$ROOT/compose.disk.yaml" \
    --project-directory "$ROOT" --project-name video-studio-disk-check)
```

`down` теперь видит только контейнеры `video-studio-disk-check-*`. Сверх того,
состав остальных контейнеров снимается до и после:

```bash
container_snapshot() { docker ps -a --format '{{.Names}}' | grep -v "^${PROJECT}" | sort; }
```

Расхождение — провал проверки, а не молчание.

## 5. Дефект 4: запись на системный диск при потерянном монтировании

Два независимых пути, оба закрыты.

**Путь первый — каталог без монтирования.** Если SSD не смонтирован,
`/srv/video-studio-data` остаётся обычным каталогом на корневой файловой
системе, и привязка тома увела бы пробы туда. Проверка спрашивает именно точку
монтирования:

```bash
findmnt -no TARGET -M "$MOUNT"
```

Измерено на mini-server: для каталога, который точкой монтирования не является,
`findmnt -no TARGET /home/igor` даёт код 1. Раздел при этом жив, поэтому
`-M` — не формальность: он отделяет «каталог существует» от «каталог
смонтирован».

**Путь второй — источник совпал с корнем.** Ветка `/dev/mapper/*` раньше
печатала «источник — логический том» и этим ограничивалась. Корень этого
хоста — `/dev/mapper/ubuntu--vg-ubuntu--lv`, то есть корневая файловая система
проходила проверку как хранилище. Добавлено сравнение с источником `/`:

```bash
root_source=$(findmnt -no SOURCE /)
[ "$source" != "$root_source" ] || bad "источник … корневая файловая система"
```

**Путь третий — подмена раздела внутри контейнера.** Даже если хостовые
проверки пройдены, контейнер обязан видеть отдельную файловую систему:

```bash
inside_dev=$(docker exec "$cid" stat -c %d /out)
container_dev=$(docker exec "$cid" stat -c %d /)
[ "$inside_dev" != "$container_dev" ] || bad "/out на корневой файловой системе контейнера"
```

## 6. Запрет `--fill` сохранён

Ворота остались на месте и срабатывают до запуска контейнера:

1. `MOUNT` равен рабочему пути — отказ;
2. серийный номер источника равен рабочему — отказ (запасная линия: при
   текущем порядке до неё дело не доходит, потому что тождество уже дало
   провал выше; линия остаётся на случай, если проверку тождества ослабят);
3. размер больше 16 GiB — отказ;
4. нет файла `.fill-test-ok` в хранилище — отказ.

Добавлены имитации, повторяющие поведение настоящих утилит:

- `findmnt` различает `-M` и запрос источника корня — иначе проверка «каталог
  внутри раздела» и «источник не корень» проходила бы молча;
- `docker` моделирует compose с именем проекта, `exec` внутри контейнера и
  снимок контейнеров, а каждый вызов пишет в журнал, поэтому «к чему скрипт
  обращался» проверяется по факту, а не по намерению.

## 8. Что не выполнялось

- `verify-storage.sh` на сервере не запускался: он поднимает контейнер, а это

- `sudo`, `wipefs`, `mkfs`, `sgdisk`, `mount`, правка `fstab`, перезагрузка —

## 9. Безопасная проверка дискового режима

Выполнять по шагам, каждый шаг обратим.

```bash
cd /home/igor/video-studio

./host/check-storage.sh          # 1. состояние, только чтение
./scripts/verify-storage.sh      # 2. базовые проверки, временный контейнер своего проекта
MODE=disk ./scripts/run-render.sh \
  -f lavfi -i testsrc=size=640x360:rate=25 -t 2 \
  -c:v libx264 -preset veryfast -y /out/probe.mp4     # 3. около 200 КБ
ls -l /srv/video-studio-data/out/probe.mp4            # 4. файл дошёл до диска
rm -f /srv/video-studio-data/out/probe.mp4            # 5. убрать пробу
```

Ожидаемое на шаге 2: `ext4`, источник `/dev/sdc1`, «рабочий SSD 24257G400264,
как и требуется», `/out` на отдельной файловой системе, «состав остальных
контейнеров не изменился».

Ожидаемое на шаге 3: строка ограды «квота 926 GiB действует» и файл около
200 КБ. Шаг 3 пишет только один короткий файл; `--fill` не используется.

## 10. Остаточные риски

| Риск | Оценка | Чем закрыт |
|---|---|---|
| SSD отвалился между проверкой и `up` | низкий | внутри контейнера сверяются размер с маркером и раздел `/out` ≠ `/` |
| `docker compose down` в чужом проекте | низкий | своё имя проекта; чужой `studio` не входит в него |
| Кто-то ослабит проверку тождества и `--fill` пройдёт | низкий | запасные ворота по серийному номеру сохранены |
| `STORAGE_ROOT` попадёт в рабочий контейнер из окружения | низкий | переменная задаётся только внутри проверки и `run-render.sh`; значение по умолчанию — рабочий путь |
| Запись пробы при полуживом USB-мосте | низкий | размер и раздел проверяются до записи; при `ENOSPC` ограда вернёт ошибку |
