### Инженерная методика следующего фильма: максимум качества без дорогого железа и постоянных расходов

1. **Сначала сюжет и непрерывная физическая логика.** Короткий сценарий с причиной/действием/следствием; для каждой сцены записать `состояние до → физическое действие → состояние после`. Где находится персонаж, что у него в руках, на что опирается предмет, куда он смотрит, что уже сделано — фиксировать до генерации. Одно сложное физическое действие на короткий клип, не несколько одновременно. Если сцена не объясняет движение/действие — не спасать её монтажными «заплатами».
2. **Неподвижные идентичности и референсы.** До видеогенерации утвердить образ персонажа (включая очки, сумку/инструменты, детали корпуса при наличии), цветка, конкретное расположение объектов, окружение, цвет и свет. Хранить единые референсные кадры/модельный лист и проверять каждую сцену. Созданные ранее варианты ChatGPT, Google Flow и загруженные изображения/видео использовать как **материал для анализа и опоры**, а не начинать с нуля. Файлы, доступные только в текущем чате, **не считать автоматически сохранёнными в GitHub/на SSD**; при следующей задаче восстановить/передать из действительных источников.
3. **Связь генераций.** Для следующей сцены применять конечный кадр предыдущей как `start frame` (или согласованные начальный/конечный кадры), использовать в Google Flow `Ingredients` для постоянных персонажей/объектов/стиля. Вместо независимых длинных текстовых промптов — преемственные кадры и единый набор визуальных ориентиров. Проверить, доступна ли нужная функция в текущем аккаунте/модели; возможности планов/лимиты не предполагать. Источники: [Google Flow: 5 советов](https://blog.google/innovation-and-ai/products/flow-video-tips/), [Google Flow Help](https://support.google.com/flow/answer/16353334?hl=en), [опыт AI-фильммейкеров: кадр-опора, сквозная композиция](https://www.reddit.com/r/aifilmmaking/comments/1y0wh1k/which_ai_video_generator_can_keep_34_shots/).
4. **Дёшево поэтапно.** Облачную генерацию делать только для нужных движущихся моментов; сценарий, статические эскизы/контакт-листы, проверку референсов и FFmpeg-монтаж выполнять доступными средствами. Mini-server с CPU и установленным FFmpeg уже достаточен для монтажа; **не покупать GPU, не арендовать машины, не оформлять новые платные сервисы без утверждения**. Прежде чем тратить квоту, проверять статичный кадр, последовательность, положения и реквизит. Перегенерировать точечно только дефектный клип; заранее согласовать допустимое число попыток/бюджет.
5. **Формат под канал.** Для TikTok предпочтительно заранее планировать **вертикальное 9:16**, соблюдая безопасные зоны от подписей и элементов интерфейса, вместо съёмки 16:9 и последующей болезненной обрезки. Ориентир — [TikTok Creative Codes, рекомендации по 9:16 и safe-space](https://ads.tiktok.com/business/library/TikTok_CreativeCodes_May2023.pdf). Учитывать объекты в центре и расстояние до нижнего/правого края; конкретный формат утверждать до генерации.
6. **Чужой опыт и альтернатива по умолчанию.** ChatGPT обязан перед предложением новых дорогих/затратных решений искать актуальную документацию, практику независимых авторов (включая Reddit), сравнивать реальные риски и предлагать **выход с меньшими затратами**. Не замыкаться на привычной генерации «ещё одной картинки», новых подписках, настройках сервера или бесконечных ревизиях. Один понятный эксперимент → просмотр владельцем → решение, стоит ли продолжать.
7. **Роли.** ChatGPT — режиссура, референсы, сравнение методов, выбор стратегии, конкретные задания и контроль качества; OpenHands — инженерное исполнение на сервере, FFmpeg, скрипты, сохранение версий, тесты, документация. ## Текущий производственный этап и следующий шаг

**Активная задача:** новый **семейный клип из Telegram-кружков и фотографий**, [Issue #13](https://github.com/prokprokopsystem/openhands-agent/issues/13). Ожидаем музыкальный файл и передачу материалов; создать средства отбора 1–3-секундных моментов, контактные листы, затем согласовать ритм и монтаж на полную длительность музыки. **Этап A выполнен 21.11.2026: инвентаризация 693 файлов и проверка музыки.** Монтаж не начинался. Режиссёрское решение — постепенная обработка и человеческий отбор, а не бесконечная случайная нарезка. Подробности в разделе «Новый активный проект» выше.

**Предыдущий фильм:** «Маленькое добро» завершён, опубликован в основном TikTok; его `v1.mp4` остаётся на SSD как технический оригинал без музыки. Ошибки непрерывности документированы. Не возобновлять его монтаж без явного запроса.

### Не делать автоматически

- Не форматировать, не перемонтировать и не перенастраивать SSD; **не трогать `/dev/sda` и `/dev/sdb` (`AMNESIA_BACKUP`)**.
- Не менять AMNESIA, Paperless, Nextcloud, OpenHands, общие Docker-настройки, не запускать `prune`.
- Не запускать тест 2 GiB/`--fill` на рабочем SSD; не устанавливать HyperFrames без отдельного задания.
- Не сливать PR #11 как побочный эффект «актуализации документов» без проверки самого кода и отдельного решения.
- Пока нет резервного копирования студийных материалов, **не удалять ни исходные MP4 на сервере, ни исходники на компьютере**.
- Не принимать старые записи UUID без чтения фактического `blkid`/`findmnt`, если UUID понадобится для операции: не использовать UUID по памяти или из старого текста как основание для привилегированных действий.

## Правило записи каждого изменения (обязательно)

После **любого** изменения сервера, кода, входных материалов, версии фильма или стадии работы:

1. Указать **что было → что стало**; конкретную дату, способ проверки, ссылку на отчёт/PR/коммит.
2. Отдельно указать: **ИЗМЕНЕНО / НЕ ИЗМЕНЕНО / ПРОЙДЕНО / НЕ ПРОВЕРЕНО / СЛЕДУЮЩЕЕ ДЕЙСТВИЕ**. План и догадку никогда не помечать «ПРОЙДЕНО».
3. Обновить именно этот файл (и профильную техническую инструкцию, если поменялась), **не копировать длинные блоки текущего статуса в README и глобальный `docs/Состояние.md`**.
4. При работе в ветке PR обеспечить, что этот файл на `main` остаётся актуальным. Если невозможно безопасно синхронизировать, явно указать **расхождение и конкретную ветку**; не маскировать его.
5. В следующем чате начинать с этого файла, затем только с актуальных задачи/кода; старые отчёты читать ради истории и доказательств.
