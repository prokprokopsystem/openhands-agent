## Что является источником истины

1. **Работающая установка на mini-server**: фактические проверенные измерения, с датой, командой и отчётом агента. Они могут опережать Git.
2. **Этот файл**: последнее зафиксированное состояние, проверенные и незавершённые работы, следующее действие. При новом подтверждённом изменении обновить.
3. **Git-код:** ветка `main` — слитая версия; до слияния PR #11 работающий дисковый код хранится в ветке `video-studio-disk-storage`, а **на сервере уже установлен**. Статус «PR открыт» — не значит «сервер не настроен».
4. **Issue #12** — задачи и журнал обсуждения, но не отдельная конкурирующая версия текущего статуса.
5. **Датированные отчёты, старые планы и Google Drive** — история, концепции и результаты на дату записи. Они не отменяют более поздние проверенные факты. Google Drive не обязан быть доступен OpenHands.

**Важно:** файл `docs/Состояние.md` описывает прежде всего **сам OpenHands**; в разделе видеостудии должна быть только ссылка сюда, без второй копии статуса. `docs/video-studio/README.md` — навигация, а не самостоятельный журнал текущего состояния.

## Текущий производственный этап и следующий шаг

**Этап:** первый фильм «Маленькое добро» (также в творческих обсуждениях «Сон моей доброты»). **Генерация пяти видеоклипов завершена, файлы доставлены на SSD; сейчас инвентаризация перед монтажом.** Близость названий не означает два разных текущих проекта.

1. OpenHands запускает из действующей установки `./scripts/inventory-sources.sh /srv/video-studio-data/in/maloe-dobro` (без удаления/перемещения исходников).
2. Сообщает действительные длительности, параметры видео/аудио, хэши, дубли и полные имена; готовит согласованный **монтажный план**, включая точные монтажные границы проблемной сцены №3.
3. Пользователь и ChatGPT утверждают порядок/обрезку, титр и звуковую концепцию. **Реальный художественный рендер только после согласования.**
4. OpenHands производит `MODE=disk` рендер через защищённый FFmpeg, проверяет `ffprobe`, отдаёт MP4 для просмотра и уточнений.
5. После завершения реального шага агент **в этом же задании** меняет здесь статус, ссылки на вывод/commit и дату. Отчёт в чате без этой правки — **не зафиксированное завершение**.

### Не делать автоматически

- Не форматировать, не перемонтировать и не перенастраивать SSD; **не трогать `/dev/sda` и `/dev/sdb` (`AMNESIA_BACKUP`)**.
- Не менять AMNESIA, Paperless, Nextcloud, OpenHands, общие Docker-настройки, не запускать `prune`.
- Не запускать тест 2 GiB/`--fill` на рабочем SSD; не устанавливать HyperFrames без отдельного задания.
- Не сливать PR #11 как побочный эффект «актуализации документов» без проверки самого кода и отдельного решения.
- Пока нет резервного копирования студийных материалов, **не удалять ни исходные MP4 на сервере, ни исходники на компьютере**.
- Не принимать старые записи UUID без чтения фактического `blkid`/`findmnt`, если UUID понадобится для операции: не использовать UUID по памяти или из старого текста как основание для привилегированных действий.

## Правило записи каждого изменения (обязательно)

После **любого** изменения сервера, кода, входных материалов, версии фильма или стадии работы:

1. Указать **что было → что стало**; конкретную дату, способ проверки, ссылку на отчёт/PR/коммит.
2. Отдельно указать: **ИЗМЕНЕНО / НЕ ИЗМЕНЕНО / ПРОЙДЕНО / НЕ ПРОВЕРЕНО / СЛЕДУЮЩЕЕ ДЕЙСТВИЕ**. План и догадку никогда не помечать «ПРОЙДЕНО».
3. Обновить именно этот файл (и профильную техническую инструкцию, если поменялась), **не копировать длинные блоки текущего статуса в README и глобальный `docs/Состояние.md`**.
4. При работе в ветке PR обеспечить, что этот файл на `main` остаётся актуальным. Если невозможно безопасно синхронизировать, явно указать **расхождение и конкретную ветку**; не маскировать его.
5. В следующем чате начинать с этого файла, затем только с актуальных задачи/кода; старые отчёты читать ради истории и доказательств.
