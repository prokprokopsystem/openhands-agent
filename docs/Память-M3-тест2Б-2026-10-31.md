## 2. Инвентарь штатных API (проверено на практике, не по документации)

| API | Что даёт | Ограничение |
|---|---|---|
| `update(memory_id, metadata={...})` | сливает metadata с существующим payload (`new_metadata = deepcopy(payload)`, затем `.update(...)`), текст и `created_at` сохраняет, пишет событие `UPDATE` в history | не влияет на поиск сам по себе |
| `update(memory_id, expiration_date=...)` | ставит `expiration_date`, запись скрывается из `search`/`get_all` по умолчанию | сравнение строго `< сегодня`, то есть срабатывает только со следующего дня; дата, а не отношение |
| `get(memory_id)` | возвращает `memory` + `metadata` целиком | — |
| `search(..., filters={...})` | любые пары ключ/значение уходят в Qdrant как `FieldCondition` | фильтр по метаданным действует, только если ключ есть у записи |
| `search(..., show_expired=True)` | возвращает и просроченные | — |
| `get_all(..., show_expired=...)` | то же для листинга | — |
| `history(memory_id)` | все события `ADD`/`UPDATE` с временем | — |

Дополнительно: `uuid_mapping` внутри `_add_to_vector_store` — `main.py:937,939` — **создаётся и нигде не читается**. Внешнего способа получить соответствие «индекс → UUID» Mem0 не предоставляет.

## 4. Сопоставление индексов с реальными ID — доказательство

Индексы `"0"`,`"1"` из ответа модели — не ID. Соответствие восстановлено по трём независимым свидетельствам:

1. **Промпт, который получила модель.** Секция `## Existing Memories` содержала ровно 2 элемента с `"id": "0"` и `"id": "1"` и полными текстами. То есть под индексом лежит конкретный текст, а не позиция в чьём-то списке.
2. **Уникальное совпадение текста.** Каждый текст из промпта совпал ровно с одной сохранённой записью: `0 → 47230f3d`, `1 → f632a54d` (2 из 2 разрешены однозначно).
3. **Порядок выдачи векторного поиска.** Перехваченный во время `add()` результат `vector_store.search` дал тот же порядок: `index 0 → 47230f3d`, `index 1 → f632a54d`. Совпадение порядка с промптом подтверждено.

Вывод: **сопоставление надёжно восстановимо и проверяемо** — при условии, что мы перехватываем либо промпт, либо результат поиска. Штатно Mem0 этого не отдаёт (см. `uuid_mapping`), поэтому перехват — уже наша логика, зависящая от внутреннего устройства промпта и порядка выдачи.

## 10. Что Mem0 умеет сам, а что потребовало дополнительной логики

**Штатно, без ничего своего:**

1. `update(memory_id, metadata={...})` — слияние метаданных с сохранением текста и `created_at`, с записью `UPDATE` в history. Это и есть носитель `superseded_by`.
2. `get(memory_id)` — отдаёт `superseded_by` целиком.
3. `expiration_date` — скрывает запись из `search` и `get_all` **по умолчанию**, без участия вызывающего.
4. `show_expired=True` — возвращает скрытое; фильтр по метаданным (`status=superseded`) даёт ровно исторический срез.
5. Фильтрация по произвольным ключам metadata в `search`/`get_all`.
6. Полный аудит в `history` (`ADD` + `UPDATE` с временем).

**Потребовало дополнительной логики:**

1. **Получение соответствия «индекс → UUID».** Mem0 строит `uuid_mapping` и выбрасывает его. Пришлось перехватывать `vector_store.search` во время `add()` и/или разбирать секцию промпта. Работает, но опирается на внутреннее устройство Mem0: изменится формат промпта или порядок выдачи — сопоставление сломается молча.
2. **Решение, какую запись отменять.** Даже с восстановленным соответствием выбор делает вызывающий: сигнал модели неполон (1 из 2 записей про K2).
3. **Сплошная разметка `status`.** Фильтр `{"status": {"ne": "superseded"}}` работает только если **все** записи имеют этот ключ, иначе выпадают все (проба 2: 0 попаданий). Значит разметку надо ставить каждой записи при создании.
4. **Исключение по умолчанию.** Через metadata-флаг — требует, чтобы каждый вызывающий добавлял фильтр, то есть изменения в хуке чтения. Через `expiration_date` — не требует, но дата должна быть обратной (сегодняшняя не исключает), то есть запись «просрочена вчера» уже в момент отмены.
5. **Связь «отменяющее → отменённое»** хранится только потому, что мы сами положили её в metadata. Mem0 о ней не знает и при поиске не учитывает.

## 11. Остановка: конкретное препятствие

Требование «не должно возникнуть двух одновременно действующих противоречащих решений» **не выполнено штатными средствами**, и препятствие конкретное:

**Полнота сигнала отмены не гарантируется и не проверяема изнутри Mem0.** Модель возвращает `linked_memory_ids` по своему усмотрению: в тесте №2 на тех же двух репликах она назвала обе записи раунда А, в тесте №2Б — только одну. Mem0 это поле не сохраняет и не валидирует, поэтому проверять полноту нечем: система не знает, сколько записей подлежало отмене. В результате «K2 — действующее решение» снято, а «K2 проверено и работоспособно» осталось активным и выдаётся обычным поиском (0.214).

Обойти это можно только внешней логикой (повторный проход по всем записям с тем же субъектом, собственный признак актуальности, ручная сверка) — то есть тем, что в задании делать запрещено. Механизм актуализации рабочий, но он **не самодостаточен**: без решения вопроса полноты сигнала он снимает не все устаревшие утверждения.

Дополнительное ограничение, зафиксированное отдельно: `expiration_date` даёт исключение только со следующего дня (сегодняшняя дата не исключает), а metadata-флаг сам по себе не исключает ничего.
