## 1. Замысел и ограничения владельца

- Сохранить простой работающий OpenHands с Canvas, DeepSeek Flash, существующими подключениями и автозапуском; долговременная память должна работать в новых чатах автоматически, без новой внешней LLM для поиска, дополнительных сервисов и контейнеров.
- Использовать Mem0 как локальный **поисковый индекс и память о фактах**, а канонические проектные документы — как источник действующего состояния и решений.
- **AMNESIA и Nextcloud неприкасаемы:** никакого изменения их действующей инфраструктуры, конфигурации, MCP, авторизации, баз, контейнеров или данных ради OpenHands.
- Идею когда-нибудь создать **независимую** систему общей памяти по архитектурному образцу AMNESIA обсуждали только теоретически. Она **не реализована, не разрешена к развёртыванию**. Копирование подходов/кода из репозитория не означает использования оригинального сервиса, его данных и ключей.
- Экономия токенов и ресурсов мини-сервера; без ненужных бэкапов и перестройки имеющихся служб. Документировать подтверждённые изменения в GitHub.

## 4. Как устроена память и почему она не всемогуща

1. При отправке запроса хук вызывает локальный семантический поиск, возвращая несколько релевантных фрагментов контекста. Поиск не вызывает внешнюю LLM, но требует запуска FastEmbed и может заметно задерживать ответ.
2. `stop` захватывает новые реплики по курсору в JSONL-очередь; на завершении беседы или старте следующей выполняется `mem.add(infer=True)` с извлечением фактов. Запись одной пачкой — до 40 сообщений, не более 3 пачек за запуск (точные параметры в текущем конфиге).
3. Идемпотентность: `batch_id=sha256(conv_id | event_ids)`; `store_lock` защищает доступ к embedded Qdrant. **Нельзя просто открыть один каталог Qdrant из второго процесса** — возможен конфликт эксклюзивной блокировки.
4. Если процесс оборван до события захвата, последние реплики не гарантированы; очередь может обрабатываться с задержкой. Области памяти: обычный чат = general, проектный — свой project_id плюс ограниченное количество общих фактов. Одинаковые имена проектных каталогов способны конфликтовать.
5. Семантический поиск может вернуть старые и нерелевантные факты. `Mem0 infer=True` не обеспечивает гарантированного удаления/замены противоречий; метка `superseded_by` не заполняется автоматически во всех случаях. Утверждения о текущем состоянии нужно проверять в документации.
6. Хуки могут деградировать без остановки чата. Успешный ответ OpenHands сам по себе не доказывает, что память участвовала; проверять журналы и путь источника, а не уверенный тон модели.

## 5. Ошибка, которую обнаружили, и как исправили

**Симптом:** новый чат сообщил «модернизация backup подготовлена, но НЕ установлена», хотя пользователь установил её 31.10 и в §8 документа это уже было записано.

**Причины:** (а) агент читал `/tmp/oha` на `22f4f05`, а удалённая ветка продвинулась; локальный `git status` без `fetch` не выявляет отставания; (б) в шапке отчёта, `План.md`, `Состояние.md` и `MEMORY.md` сохранялись старые статусы; (в) `AGENTS.md` не требовал сверки актуального remote HEAD; (г) Mem0 может содержать исторические факты с формулировкой настоящего времени.

**Исправление (коммит `94201fc`):** главный статус вынесен в верх `docs/Состояние.md`; `docs/План.md`, шапки отчётов и backup §7 обновлены без удаления исторических протоколов; `AGENTS.md` правило 11 требует ссылаться на действующий документ, правило 12 — при выводах о текущем состоянии сверять удалённую ветку с локальным HEAD; актуализированы локальный `MEMORY.md` и датированный журнал. **Исправления поведенческие/документальные, не программная гарантия.**

**Повторный тест 01.11:** агент проверил GitHub PR #4 на HEAD `94201fc`, прочитал документы удалённой ветки, сообщил верный статус установки, обнаружил и отбросил два неудачных кандидата recall (один устаревший, один посторонний). Это подтверждает **этот сценарий**, а не абсолютную надёжность на всех задачах.

## 6. Что намеренно НЕ делали

- Не меняли Mem0, FastEmbed, embedded Qdrant, `hook_recall.py`, `hook_capture.py`, `hook_write.py`, Docker, Compose, systemd или профили модели ради исправления актуальности.
- Не трогали рабочие AMNESIA/Nextcloud и их инфраструктуру.
- Не внедряли общий доступ ChatGPT ↔ OpenHands к Mem0. Идея **отдельного независимого клона/архитектурного образца AMNESIA** только обсуждалась, проект не создавали.
- Не считали PR #4 влитым в `main`; на момент проверки 01.11 PR открыт, актуальные документы находятся в ветке PR.
- Не считали документирование результатов испытаний равным полной приёмке или полному restore.

## 7. Незакрытые риски и наблюдение в испытательный период

| Область | Открыто / риск | Что проверять при обычной работе |
|---|---|---|
| Актуальность | Локальные файлы и Mem0 могут отстать от канонического документа; агент может забыть правило | Сверяет ли remote и `docs/Состояние.md` на вопрос о действующем статусе |
| Качество памяти | Шум/устаревшие фрагменты; не все факты извлекаются | Конкретный вопрос → какой фрагмент найден → источник → ответ |
| Очереди | Отложенная запись, 3 пачки за старт; возможна потеря хвоста | `stage1/writes.jsonl`, backlog, ошибки; отсутствие факта не означает поломку |
| Производительность | На recall около 3–5 с дополнительной задержки | Пауза на сообщениях; сравнение с логами |
| Qdrant | Embedded lock: один владелец каталога | Не запускать конкурирующий reader/writer на live DB |
| Backup | Не доказаны production SKIP/ротация, полное restore, полное сравнение архивов | Позже проверить **уже прошедшие штатные** запуски, без вмешательства в расписание |
| Безопасность backup | Архивы не шифруются, содержат секреты; второй носитель отсутствует | Считать осознанным открытым риском, не публиковать секреты/архивы |
| Репозиторий | PR №4 открыт; main старее; вне Git есть рабочая память | Не делать deploy из устаревшего main; отдельно оценить, когда и как оформлять завершение PR |

**Отдельный обнаруженный пробел:** тест 01.11 зафиксировал, что плановый запуск `openhands-backup.timer` должен был случиться около 00:12 UTC, но агент не имел подтверждённого результата. Не делать вывод об успешности или сбое без журнала.

## 8. Как продолжать через некоторое время

1. Перед выводами о состоянии открыть `AGENTS.md`, `docs/Состояние.md` и эту сводку **в самой свежей ветке**, затем первичные документы по конкретному вопросу.
2. Сверить удалённый HEAD с локальным: `git ls-remote origin feat/persistent-memory-pilot-20261031` vs `git rev-parse HEAD`. Если локальный checkout старый, читать новую версию из GitHub или аккуратно обновить checkout; не заменять работающие серверные файлы без сравнения.
3. Снять **read-only** факты о работе памяти: журнал recall, журнал записи, ошибки, очереди, реальные сообщения пользователя, не публикуя личные данные и секреты. Не открывать embedded Qdrant параллельно с другим процессом без соблюдения блокировки.
4. Проверить реальную работу по нескольким новым чатам: извлечение известных фактов, отсеивание устаревших, сохранение новых фактов после SessionEnd/SessionStart, разделение general/project, время отклика.
5. Если обнаружена ошибка — сначала классифицировать: **не записано / не найдено / найдено устаревшее / документ устарел / ветка отстала / блокировка базы / задержка**. Исправлять конкретную причину, не переписывая рабочую архитектуру по умолчанию.
6. Любое последующее подтверждённое изменение отразить в `docs/Состояние.md`, `docs/План.md` по необходимости и этом журнале отдельной датированной записью; сохранять историю Git и первичные доказательства.

## 9. Критерии следующей оценки

Пилот пока **в эксплуатации для наблюдения**, не объявлен полностью завершённым. Оценивать: сохраняется ли контекст между чатами; не выдаются ли старые решения за действующие; нет ли заметных зависаний и ошибок; не растёт ли очередь; не мешает ли запись обычным задачам; работают ли штатные бэкапы. По итогам решить: оставить как есть, точечно исправить дефект либо отключить `enabled: false` (только по отдельному решению владельца).
