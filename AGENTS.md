# Обязательные правила работы

1. Перед работой прочитать:
   - `docs/Состояние.md` — фактическое состояние;
   - `docs/План.md` — текущий этап;
   - относящиеся к задаче решения из `docs/Решения.md`;
   - соответствующую инструкцию из `deployment/`.

2. Зафиксированное в документации состояние считается действующим, пока после него не задокументировано реальное изменение.

3. Запрещено повторно полностью проверять mini-server, если после последней проверки не было задокументированных изменений.

4. Повторная проверка разрешена только когда:
   - сервер действительно изменён;
   - предыдущая проверка завершилась ошибкой;
   - для следующего действия нужен конкретный факт, отсутствующий в документации.

5. Перед повторной проверкой кратко указать, какое новое изменение или неизвестный факт её вызвали. Без такой причины проверку не выполнять.

6. Не начинать рассуждение и исследование проекта с нуля. Использовать канонические документы и историю Git.

7. После любого реального изменения кода, конфигурации или mini-server в той же работе:
   - обновить `docs/Состояние.md` — раздел «Текущее состояние» с датой;
   - обновить связанную инструкцию;
   - при изменении этапа обновить `docs/План.md`;
   - зафиксировать код и документацию одним завершённым коммитом.
   Изменение, выполненное владельцем сервера по инструкции агента, агент фиксирует
   в `docs/Состояние.md` в тот же рабочий день со ссылкой на подтверждение: документ,
   раздел, дата. Ждать следующего этапа нельзя.

8. Изменение без обновлённой документации не считается завершённым.

9. Теоретический риск не является препятствием. Остановка допустима только при подтверждённой ошибке, выходе за разрешённые границы или реальном риске повреждения защищённых систем.

10. Отчёты писать простым русским языком: «ПРОЙДЕНО», «НЕ ПРОЙДЕНО», «ИЗМЕНЕНО», «НЕ ИЗМЕНЕНО».

11. Утверждение о текущем состоянии проекта допустимо только со ссылкой на канонический документ, раздел и дату. Сначала прочитать `docs/Состояние.md` (раздел «Текущее состояние»), затем относящийся к теме документ и `docs/План.md`. Если в документе есть более поздняя запись, действует она. Память агента (`MEMORY.md`, Mem0) — указатель, а не источник истины: при расхождении прав документ.

12. Если работа идёт через GitHub или вывод опирается на документ из репозитория, перед утверждением о текущем состоянии проверить свежесть ветки: `git ls-remote origin <branch>` и сравнить с `git rev-parse HEAD`. При расхождении — `git fetch` и читать документ на актуальном коммите, а не на локальной копии. `git status` без `fetch` отставшую копию не выявляет. Это проверка перед выводами о состоянии, а не при каждом обычном сообщении.
