# Обязательные правила работы

1. Перед работой прочитать:
   - `docs/Состояние.md` — фактическое состояние;
   - `docs/План.md` — текущий этап;
   - относящиеся к задаче решения из `docs/Решения.md`;
   - соответствующую инструкцию из `deployment/`.

2. Зафиксированное в документации состояние считается действующим, пока после него не задокументировано реальное изменение.

3. Запрещено повторно полностью проверять mini-server, если после последней проверки не было задокументированных изменений.

4. Повторная проверка разрешена только когда:
   - сервер действительно изменён;
   - предыдущая проверка завершилась ошибкой;
   - для следующего действия нужен конкретный факт, отсутствующий в документации.

5. Перед повторной проверкой кратко указать, какое новое изменение или неизвестный факт её вызвали. Без такой причины проверку не выполнять.

6. Не начинать рассуждение и исследование проекта с нуля. Использовать канонические документы и историю Git.

7. После любого реального изменения кода, конфигурации или mini-server в той же работе:
   - обновить `docs/Состояние.md`;
   - обновить связанную инструкцию;
   - при изменении этапа обновить `docs/План.md`;
   - зафиксировать код и документацию одним завершённым коммитом.

8. Изменение без обновлённой документации не считается завершённым.

9. Теоретический риск не является препятствием. Остановка допустима только при подтверждённой ошибке, выходе за разрешённые границы или реальном риске повреждения защищённых систем.

10. Отчёты писать простым русским языком: «ПРОЙДЕНО», «НЕ ПРОЙДЕНО», «ИЗМЕНЕНО», «НЕ ИЗМЕНЕНО».

## Начало нового чата

Этот порядок действует в каждом новом чате и не заменяет правила выше. Тот же
текст загружается как глобальная инструкция агента (см. `deployment/README.md`,
раздел «Где хранятся глобальные инструкции»).

1. Новый чат — новая беседа того же постоянного агента, а не новая установка.
2. Не объявлять потерю доступов только потому, что локально отсутствуют `/srv`,
   Docker socket или SSH-ключ в `~/.ssh`.
3. Если пользователь назвал проект: найти только соответствующий каталог в
   `/projects`; прочитать его `AGENTS.md`; прочитать указанный там файл текущего
   состояния; продолжить с последней зафиксированной точки.
4. Не читать и не смешивать документацию посторонних проектов.
5. Если проект из запроса однозначно определить нельзя — задать один короткий
   уточняющий вопрос, а не обследовать все репозитории.
6. Для работы с mini-server использовать существующее подключение `ssh mini-server`.
7. До объявления отсутствия доступа к mini-server проверить
   `ssh mini-server hostname` и `ssh mini-server id`.
8. Для GitHub использовать постоянную авторизацию `gh`.
9. До объявления отсутствия доступа к GitHub проверить
   `gh auth status --hostname github.com` и права на нужный репозиторий через `gh api`.
10. Если `gh` авторизован, но обычный HTTPS Git запрашивает логин, выполнить
    `gh auth setup-git --hostname github.com`.
11. Не выводить токены, приватные ключи и содержимое файлов авторизации.
12. Зафиксированное состояние проекта считать исходной точкой. Не начинать
    проектное исследование заново без подтверждённой причины.
13. Не выполнять изменения, не относящиеся к названному пользователем проекту.
14. Общая память хранит правила и предпочтения, а фактическая точка продолжения
    каждого проекта хранится в документации этого проекта.
